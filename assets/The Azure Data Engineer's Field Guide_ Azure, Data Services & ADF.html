How to Read This Guide

This is the companion to the RDBMS, SQL and Data Warehousing field guide. That guide explained what a data engineer builds (models, pipelines, warehouses). This one explains where and with what you build it on Microsoft Azure.

Every concept follows the same rhythm:

  1. The analogy (green panels) — a real-world picture so the idea clicks.
  2. The real explanation — how the service actually works.
  3. Why it matters to you — how it shows up in daily work, design decisions and interviews.
  4. Examples — expressions, SQL, JSON, KQL or configuration where useful.

A note on where Azure is heading (as of late 2026). Microsoft's strategic investment for analytics is now centred on Microsoft Fabric. Azure Data Factory (ADF) and Azure Synapse Analytics remain fully supported and are still running a huge number of production workloads, but most new features are landing in Fabric, and Microsoft has published guidance for moving ADF and Synapse pipelines into Fabric. Some ADF features, like its managed Apache Airflow option, have been deprecated for new customers. For you this means: ADF skills are still essential (they transfer almost one-to-one into Fabric Data Factory), Synapse knowledge matters for supporting and migrating existing estates, and Fabric literacy is increasingly expected. This guide covers all three, with ADF in the most depth.

Part 1: Azure foundations

1.1 Why the Cloud? Renting vs Owning

Analogy. Running your own data centre is like owning a house: you buy it up front, you fix the roof, you pay for empty rooms even when guests aren't visiting, and if you need more space, you build an extension over months. The cloud is like renting: you pay for what you use, the landlord fixes the plumbing, and you can take a bigger flat next month.

The cloud converts capital expense (buying servers) into operating expense (paying per hour, per GB, per run). It gives you elasticity (scale up for the month-end load, scale down overnight), managed services (Microsoft patches, backs up and replicates for you), and global reach. The trade-off: costs are continuous and easy to lose track of, and you must understand each service's responsibilities and limits.

1.2 IaaS, PaaS, SaaS: The Pizza Analogy

Analogy. You want pizza tonight. - On-premises: make it at home — buy the oven, the flour, everything. You do all of it. - IaaS (Infrastructure as a Service): rent a kitchen with an oven; you still bring ingredients, cook and clean. - PaaS (Platform as a Service): order from a takeaway — they cook it, you just provide the table and drinks. - SaaS (Software as a Service): dine in at a restaurant — everything is done for you; you just eat.

Model You manage Microsoft manages Data examples
IaaS OS, patches, database engine, backups, HA Hardware, networking, data centre SQL Server on an Azure VM
PaaS Data, schema, queries, access, configuration OS, engine patching, backups, HA Azure SQL Database, ADF, Synapse, Databricks
SaaS Your content and settings Nearly everything Microsoft Fabric, Power BI, Microsoft 365

The shared responsibility model: Microsoft is always responsible for the physical security of data centres; you are always responsible for your data, who can access it, and how it is classified. Everything in between shifts depending on the model. A huge share of real cloud data breaches come from customer-side misconfiguration (a public storage container, an over-privileged identity, a leaked key), not from the provider.

1.3 The Azure Hierarchy: How Everything Is Organised

Analogy: a large corporation. - The tenant (Microsoft Entra ID) is the company itself, with its staff directory. - Management groups are divisions (Retail, Finance), each with company-wide rules. - Subscriptions are department budgets with their own bill: dev, test and prod usually get separate ones. - Resource groups are project folders: everything for one solution, created, secured and deleted together. - Resources are the individual items in the folder: a storage account, a data factory, a SQL database.

flowchart TB
    T[Entra ID tenant<br/>the company] --> MG1[Management group: Data Platform]
    MG1 --> S1[Subscription: data-prod]
    MG1 --> S2[Subscription: data-nonprod]
    S1 --> RG1[Resource group: rg-sales-dw-prod]
    RG1 --> R1[ADLS Gen2 storage]
    RG1 --> R2[Data Factory]
    RG1 --> R3[Azure SQL / Synapse]
    RG1 --> R4[Key Vault]

Why it matters: - Permissions inherit downwards. A role granted at subscription level applies to every resource group and resource inside it. Grant at the lowest level that works. - Policies inherit downwards too (Section 2.7). - Billing is per subscription, broken down by resource group and tags. - Lifecycle: deleting a resource group deletes everything in it — useful for tearing down test environments, dangerous in production (use resource locks: CanNotDelete or ReadOnly).

1.4 Regions, Availability Zones and Region Pairs

Analogy. - A region is a city where Microsoft has data centres (e.g., Central India, Australia East, West Europe). - Availability zones are separate buildings in different neighbourhoods of that city, each with independent power, cooling and network. A fire in one building doesn't affect the others. - A region pair is a sister city hundreds of kilometres away, used for geo-redundant copies and coordinated maintenance.

Design rules: - Keep data and compute in the same region to avoid latency and cross-region data transfer (egress) costs, and to meet data residency requirements. - Use zone-redundant options for production where available (ZRS storage, zone-redundant SQL). - For disaster recovery, replicate to a second region (often the pair) — Part 8 covers this.

1.5 How You Talk to Azure: Azure Resource Manager

Analogy: whether you place an order in the shop, by phone, or through the website, it ends up at the same order desk. That desk checks your identity, checks you're allowed to order, and processes it.

Every action — through the Azure Portal, Azure CLI, PowerShell, REST API, ARM/Bicep templates or Terraform — goes through Azure Resource Manager (ARM), which authenticates you, checks RBAC and policy, and then creates or changes resources.

Infrastructure as Code (IaC) — describing resources in files (Bicep, ARM JSON, Terraform) and deploying them through pipelines — is the professional standard. Clicking in the portal is fine for learning, but production environments should be reproducible from code (Part 9).

1.6 Naming and Tagging: Labels on Every Box

Analogy: in a warehouse with thousands of identical boxes, the label is everything. A box labelled "stuff" is useless; a box labelled "Sales – Prod – Owner: Data Team – Cost centre 4410" can be found, billed and disposed of correctly.

Adopt a naming convention (Microsoft's Cloud Adoption Framework is a common basis): <type>-<workload>-<env>-<region>-<instance>, e.g. adf-salesdw-prod-cin-01, stsalesdwprodcin01 (storage account names allow only lowercase letters and numbers, 3–24 characters, globally unique), kv-salesdw-prod-cin.

Apply tags to every resource: environment, owner, cost-centre, application, data-classification. Tags power cost reports, ownership lookups and automation. Enforce them with Azure Policy.

Part 2: Identity, security and networking

2.1 Microsoft Entra ID: The Passport Office

Analogy. A passport office issues identities that every country (application) trusts. You don't need a separate ID card for every shop; you show your passport, and each shop decides what you may do inside.

Microsoft Entra ID (formerly Azure Active Directory) is Azure's identity provider. It holds:

  • Users — people.
  • Groups — collections of users (always grant access to groups, not individuals).
  • App registrations / service principals — identities for applications.
  • Managed identities — identities for Azure resources themselves.

Authentication protocols are OAuth 2.0 / OpenID Connect; services receive tokens rather than passwords.

2.2 Service Principals vs Managed Identities: The Robot's Badge

Analogy. Your company employs a robot that carries files between departments. - A service principal with a client secret is like giving the robot a badge plus a written password on a card. Someone must store that card safely, and renew it before it expires (or the robot gets locked out at 2 am). - A managed identity is like the building recognising the robot by its built-in chip. There's no password card to lose, leak or renew — Azure manages the credential automatically.

Service principal (with secret/certificate) Managed identity
Credential Secret or certificate you manage and rotate Managed by Azure, invisible to you
Risk Secrets leak, expire, get hard-coded No secret to leak
Works from Anywhere (on-prem, other clouds, CI/CD) Azure resources only
Typical use External tools, some CI/CD scenarios ADF, Databricks, Functions, VMs accessing Azure services

Two kinds of managed identity: - System-assigned — created with the resource and deleted with it. A chip built into one specific robot. Every Data Factory has one automatically. - User-assigned — a standalone identity you create and attach to one or more resources. A chip you can move between robots. Useful when several resources need the same permissions, or when you want the identity to survive resource re-creation.

Rule: prefer managed identities wherever both sides support Entra authentication (ADF → ADLS, ADF → Azure SQL, ADF → Key Vault, Databricks → storage). Fall back to secrets in Key Vault only when you must.

2.3 Azure RBAC: Control Plane vs Data Plane

Analogy. In a hotel: - The facilities manager's key lets you install, move or remove lockers in the hotel (the control plane: create, configure, delete resources). - A locker key lets you open a locker and take out what's inside (the data plane: read and write the actual data).

Being allowed to install lockers doesn't automatically mean you can open everyone's locker.

Role-Based Access Control (RBAC) = security principal (who) + role definition (what) + scope (where).

Common role Plane Grants
Owner Control Everything, including assigning roles
Contributor Control Create/manage resources, cannot assign roles
Reader Control View resources
Data Factory Contributor Control Create and manage data factories
Storage Blob Data Reader / Contributor / Owner Data Read / write / manage ACLs on blob/ADLS data
Key Vault Secrets User Data Read secret values

Classic gotcha: an engineer is Owner of a storage account but gets "This request is not authorized" when reading files. Owner is a control-plane role; reading data via Entra needs a data-plane role such as Storage Blob Data Reader. Same pattern applies to Key Vault (with RBAC permission model) and to databases (Azure SQL needs a database user for the identity, Section 4.6).

Least privilege: grant at the narrowest scope (a container or resource, not a subscription), to groups, with the narrowest role. Use Privileged Identity Management (PIM) for just-in-time elevation to admin roles.

2.4 Azure Key Vault: The Bank Locker

Analogy. You don't keep your jewellery in your coat pocket. You keep it in a bank locker: the bank guards it, records every visit, and only authorised people get in. When you need it, you go to the bank, take it out, use it, and the record shows you did.

Key Vault stores secrets (passwords, connection strings, API keys), keys (encryption keys, including customer-managed keys for TDE and storage) and certificates.

How ADF uses it: create a Key Vault linked service, grant the factory's managed identity the Key Vault Secrets User role (or an access policy with Get/List on secrets), and reference secrets in other linked services. The secret is fetched at runtime and never stored in ADF's JSON or your Git repository.

Good practice: one vault per application per environment (kv-salesdw-dev, kv-salesdw-prod) so a dev pipeline can never read prod secrets; enable soft delete and purge protection; use the RBAC permission model; monitor access logs; set expiry dates and rotate secrets.

2.5 Networking: The Gated Community

Analogy. - A Virtual Network (VNet) is a gated community with its own internal roads. - Subnets are streets within it, grouping houses with similar purposes. - A Network Security Group (NSG) is the security guard's checklist at each street entrance: which visitors may enter or leave, on which doors (ports). - A public endpoint is the house's front door on the main road: anyone on the internet can knock (even if the lock is strong). - A private endpoint is a private tunnel from inside the community straight into the service's back room. Traffic never touches the public road. - A firewall is the main gate of the community, inspecting everything entering or leaving.

Key services and concepts for data engineers:

  • Public network access + firewall rules: by default many PaaS services (storage, SQL, Key Vault) have a public endpoint. You can restrict it to specific IP ranges or selected VNets, or disable it entirely.
  • Service endpoints: let traffic from a subnet reach a PaaS service over Azure's backbone, and let the service's firewall allow that subnet. The service still uses its public IP.
  • Private endpoints (Private Link): give the PaaS service a private IP inside your VNet. Combined with disabling public access, the service becomes unreachable from the internet. This is the standard for sensitive production data.
  • Private DNS zones: make the service's normal hostname (e.g., mystorage.dfs.core.windows.net) resolve to the private IP inside your network. Most private endpoint "it can't connect" problems are DNS problems.
  • ExpressRoute / VPN gateway: private connectivity between your on-premises network and Azure.

For ADF specifically (detailed in Part 6): the Managed Virtual Network with managed private endpoints lets the Azure Integration Runtime reach locked-down storage and databases privately, and the Self-hosted Integration Runtime reaches on-premises or VNet-only sources.

2.6 Encryption

Analogy (from the first guide): a safe for money at rest, an armoured truck for money in transit.

  • At rest: Azure Storage, Azure SQL (TDE), Cosmos DB and others encrypt data at rest by default with Microsoft-managed keys. Regulated organisations often use customer-managed keys (CMK) in Key Vault so they control key rotation and revocation.
  • In transit: TLS 1.2+ everywhere; enforce "secure transfer required" on storage accounts and minimum TLS versions.
  • In use / column level: Always Encrypted in Azure SQL keeps sensitive columns encrypted even from DBAs.

2.7 Governance: Azure Policy and Microsoft Purview

Azure Policy — the building code.

Analogy: a city's building code says every building must have fire exits and no building may exceed 20 storeys. Inspectors refuse non-compliant plans.

Policies can deny non-compliant deployments (e.g., storage accounts with public access, resources outside approved regions, resources without required tags), audit them, or auto-remediate. Assigned at management group or subscription level, they make security the default rather than a checklist.

Microsoft Purview — the library catalogue and the classification office. Purview provides a data map and catalogue (scans ADLS, Azure SQL, Synapse, Power BI, etc.), automatic classification of sensitive data (emails, card numbers, national IDs), lineage (including ADF copy activity lineage) and data governance features. Microsoft Defender for Cloud adds threat detection and security posture recommendations across these services.

Part 3: Storage: Blob and ADLS Gen2

3.1 The Storage Account: The Warehouse Building

Analogy. A storage account is a warehouse building with its own address. Inside, it can have different sections: a bulk goods area (Blob), a shared filing room (Files), a conveyor of messages (Queues), and a simple ledger (Tables). As a data engineer, you'll live almost entirely in the bulk goods area — and specifically in its organised version, ADLS Gen2.

A storage account is identified by a globally unique name, which becomes part of its URLs:

  • Blob endpoint: https://<account>.blob.core.windows.net/<container>/<path>
  • ADLS Gen2 (DFS) endpoint: https://<account>.dfs.core.windows.net/<container>/<path>
  • In Spark/Databricks: abfss://<container>@<account>.dfs.core.windows.net/<path>

Use StorageV2 (general-purpose v2) accounts with Standard performance for data lakes (Premium is for low-latency, high-transaction workloads).

3.2 Blob Storage vs ADLS Gen2: The Mailroom vs the Filing Cabinet

Analogy. - Plain Blob storage is like a mailroom with one giant pile of envelopes, each labelled with a long name like sales/2024/10/13/file1.parquet. The slashes are just characters in the label. To "rename the folder" sales/2024/10/, staff must find every envelope whose label starts with that text and relabel each one — millions of operations. - ADLS Gen2 (a storage account with hierarchical namespace enabled) is a real filing cabinet with real folders. Renaming or moving a folder is one action, and you can lock individual folders with their own access rules.

ADLS Gen2 = Blob storage + hierarchical namespace (HNS). HNS gives:

  • True directories: atomic, fast rename and delete of folders — essential for Spark and Delta commit protocols and for "write to temp folder, then rename" patterns.
  • POSIX-style ACLs on folders and files (Section 3.5).
  • Better analytics performance with Spark, Databricks, Synapse and Fabric shortcuts.

Rule: for any analytics data lake, enable hierarchical namespace when creating the account (it can be enabled later via an upgrade process, but plan it from the start).

3.3 Access Tiers: Fridge, Freezer, Attic and Off-site Store

Analogy: you keep today's milk in the fridge (instant, but the most expensive space), meat for next month in the freezer, old photo albums in the attic, and legal documents you'll probably never need in an off-site storage unit where retrieval takes days and a fee.

Tier Use for Storage cost Access cost Minimum retention
Hot Frequently accessed, active data Highest Lowest None
Cool Infrequent access (e.g., monthly) Lower Higher 30 days
Cold Rare access, still online Lower still Higher still 90 days
Archive Long-term retention, almost never read Lowest Highest; offline, must be rehydrated (hours) before reading 180 days

"Minimum retention" means an early deletion fee if you delete or move the blob earlier.

Lifecycle management policies automate the movement — e.g., "move raw files to Cool after 30 days without modification, to Archive after 180 days, delete after 7 years". Make sure no pipeline still reads archived data: an archived blob cannot be read until rehydrated, so a backfill that touches archived raw files fails.

3.4 Redundancy: How Many Photocopies, and Where?

Analogy: you keep three photocopies of an important document. - All three in the same filing cabinet (LRS). A cabinet fire destroys all three. - In three different buildings in your city (ZRS). A single building fire is survivable. - Three in your office plus three more in a sister city (GRS). A city-wide disaster is survivable. - Three in different buildings in your city plus three in a sister city (GZRS) — the strongest protection.

Option Copies Protects against
LRS — Locally redundant 3 copies in one data centre Disk/server failure
ZRS — Zone redundant 3 copies across availability zones Data-centre (zone) failure
GRS — Geo-redundant LRS + async copy to the paired region Regional disaster
GZRS — Geo-zone redundant ZRS + async copy to the paired region Zone and regional failure
RA-GRS / RA-GZRS Same, with read access to the secondary Read availability during a regional outage

Important: redundancy protects against infrastructure failure, not against you deleting or overwriting data — the deletion is replicated faithfully. For that, you need data protection features (next).

3.5 Data Protection: Undo Buttons for the Lake

  • Soft delete for blobs and containers — the recycle bin: deleted data is retained for a configurable number of days and can be restored.
  • Blob versioning — version history like in a word processor: every overwrite keeps the previous version.
  • Point-in-time restore for block blobs (in supported configurations) — rewind containers to an earlier time.
  • Immutable storage (WORM: write once, read many) — a sealed evidence bag: time-based retention or legal holds that prevent modification or deletion, even by administrators. Used for regulatory records and ransomware protection.
  • Resource locks — prevent accidental deletion of the storage account itself.

Note: some features have constraints or differences when hierarchical namespace is enabled; check current support for your account configuration.

3.6 Access Control on the Lake: RBAC, ACLs, SAS and Keys

Analogy. A shared office building: - RBAC roles are building-wide access cards: "Storage Blob Data Reader on this container" lets you read everything in it. - ACLs (Access Control Lists) are locks on individual rooms and filing drawers: the Finance folder can be opened only by the finance group, even inside a container others can reach. - SAS tokens are valet keys: a key that works only for specific things (read only, one folder) and only until a set time. - Account keys are the master key to the whole building. Whoever holds it can do anything. You don't hand it out.

How Azure evaluates access: RBAC is checked first; if an RBAC role grants the permission, access is allowed. If not, ADLS Gen2 ACLs are evaluated.

ACL essentials (POSIX-style): - Permissions: Read (r), Write (w), Execute (x). On folders, Execute means "may traverse/enter this folder". - To read /raw/sales/2024/file.parquet, an identity needs Execute on every parent folder (/, /raw, /raw/sales, /raw/sales/2024) and Read on the file. Missing Execute on one parent is the most common ACL failure. - Access ACLs apply to the item; default ACLs on a folder are copied to new children created inside it. Changing a default ACL does not update existing children — you must apply recursively. - Assign ACLs to groups, never individuals; there is a limit on ACL entries per item.

SAS (Shared Access Signatures): - User delegation SAS (signed with Entra credentials) is preferred over account/service SAS (signed with the account key). - Keep expiry short, scope minimal, use HTTPS only. - Consider disabling shared key access on the account entirely, forcing Entra authentication.

3.7 Designing the Lake: Zones, Folders and File Formats

Zones (Medallion Layers)

Analogy (from the first guide): a water treatment plant — raw river water (bronze), purified (silver), bottled and labelled (gold).

A common layout uses separate containers (or separate storage accounts for stronger isolation):

raw / bronze      →  exact copies from sources, immutable, append-only
enriched / silver →  cleaned, deduplicated, typed, conformed (often Delta)
curated / gold    →  business-ready models and aggregates
sandbox           →  analyst / data scientist experimentation

Separate storage accounts per zone (or per environment) give clean security boundaries and independent throughput limits.

Folder Structure

raw/
  <source_system>/
    <entity>/
      ingest_date=2024-10-13/
        <entity>_20241013T020000Z_<run_id>.parquet
  • Partition folders by date using key=value naming (Hive-style), so Spark, Synapse serverless and Fabric can prune folders automatically.
  • Include the run ID or timestamp in file names so reruns don't overwrite each other unpredictably (or deliberately overwrite a partition folder for idempotency).
  • Don't over-partition: partitioning by hour, customer and product produces millions of tiny files — the small-files problem from the first guide. Aim for files of roughly 100 MB–1 GB for analytics.

File Formats

Analogy: - CSV is a handwritten note: anyone can read it, but there's no guarantee about what each column means, commas inside values cause chaos, and everything is text. - JSON is a form with labelled fields, flexible and nested, but verbose. - Parquet is a neatly bound, indexed reference book: columnar, compressed, typed, with statistics that let readers skip irrelevant pages. - Delta / Iceberg is that reference book plus a librarian's logbook recording every edition: ACID transactions, updates, deletes, MERGE, schema enforcement and time travel on top of Parquet files.

Format Strengths Weaknesses Use
CSV Universal, human-readable No types, quoting/encoding issues, slow, large Source extracts only when unavoidable
JSON Nested, self-describing Verbose, slow to scan API payloads, events in bronze
Avro Row-based, schema evolution Not ideal for analytic scans Streaming/Event Hubs Capture
Parquet Columnar, compressed, typed, fast Immutable files; no transactions alone Bronze/silver landing in ADF
Delta Lake Parquet + ACID, MERGE, time travel Needs a Delta-aware engine Silver/gold in Databricks and Fabric

ADF tip: when copying from databases to the lake, write Parquet (with Snappy compression). The Self-hosted Integration Runtime needs a Java runtime installed on its machine to write Parquet/ORC.

Part 4: Azure databases

4.1 The Azure SQL Family: Apartment, House or Land

Analogy: three ways to live in a city. - Azure SQL Database is a serviced apartment: fully furnished and maintained, cleaning included. You can't knock down walls or install your own boiler, but you never worry about maintenance. - Azure SQL Managed Instance is renting a whole furnished house: much more freedom (garden, garage, your own furniture layout) — almost everything you had in your own home — while the landlord still handles the roof and plumbing. - SQL Server on an Azure VM is renting a plot of land and building your own house: total control, total responsibility.

Azure SQL Database Azure SQL Managed Instance SQL Server on Azure VM
Model PaaS, single database (or elastic pool) PaaS, whole instance IaaS
SQL Server compatibility High, but instance-level features limited Near 100% (SQL Agent, cross-database queries, Database Mail, CLR, linked servers, Service Broker) 100%
Cross-database queries Not natively (elastic query is limited) Yes Yes
SQL Agent jobs No (use ADF, elastic jobs, Automation) Yes Yes
Networking Public endpoint and/or private endpoint Deployed inside your VNet (public endpoint optional) Inside your VNet
Patching, backups, HA Automatic Automatic Your job (with some automation helpers)
Best for New cloud apps, single-database workloads, modern ELT targets Lift-and-shift of existing SQL Server estates with instance-level dependencies Legacy needs: OS access, unsupported features, specific versions

Why this matters to you: many enterprise data platforms (including warehouse-style databases built on SQL Server patterns) run on Managed Instance because they rely on SQL Agent, cross-database queries or SSIS-era designs. Because MI lives inside a VNet, ADF reaches it through a Self-hosted IR in a peered network, a Managed VNet private endpoint, or its public endpoint (if enabled, on port 3342) — connectivity is the first thing to plan.

4.2 Purchasing Models and Service Tiers

DTU vs vCore — the set menu vs à la carte.

Analogy: a DTU (Database Transaction Unit) is a restaurant set menu: a bundled amount of CPU, memory and I/O at a fixed price — simple but inflexible. The vCore model is à la carte: choose CPU cores, memory follows, storage priced separately, and you can apply existing SQL Server licences (Azure Hybrid Benefit) to save money.

The vCore model is the modern default. Its service tiers:

Tier Analogy Architecture Use for
General Purpose A reliable family car Compute separate from remote premium storage Most workloads, balanced cost
Business Critical A car with a spare engine that takes over instantly Local SSD, Always On replicas built in, a free readable secondary Low-latency OLTP, fast failover, read scale-out
Hyperscale A modular building that adds floors on demand Distributed storage tiers, very large databases (up to ~100 TB+), fast backups/restores, named replicas Large or fast-growing databases

Serverless compute (General Purpose and Hyperscale): automatically scales between min and max vCores and (in General Purpose) can auto-pause when idle, billing only storage while paused.

4.3 High Availability, Backups and Disaster Recovery in Azure SQL

Built-in HA: every Azure SQL Database and MI has high availability built in (local replicas or remote storage with automatic failover). Enabling zone redundancy spreads replicas across availability zones.

Automated backups and PITR.

Analogy: a dashcam that records continuously, so you can rewind to any moment within the last few days.

Azure takes full, differential and log backups automatically. Point-in-time restore (PITR) creates a new database as of any moment within the retention window (configurable from 1 to 35 days, 7 by default). Long-term retention (LTR) keeps weekly/monthly/yearly full backups for up to 10 years. Backup storage redundancy can be LRS, ZRS or GRS. Geo-restore restores from geo-replicated backups into another region.

Key point: a restore creates a new database; you then copy data back or swap names/connections. Practise this before you need it.

Active geo-replication and failover groups.

Analogy: a live mirror of your shop in a sister city, kept in sync continuously; with a failover group, customers use a single shop address that automatically redirects to whichever shop is open.

  • Active geo-replication (SQL Database): readable secondary databases in other regions.
  • Failover groups (SQL Database and MI): group databases together, with listener endpoints (read-write and read-only) that stay the same after failover, so applications and ADF linked services don't need changing.

4.4 Performance and Monitoring in Azure SQL

Everything from the first guide's Part 5 applies. Azure adds:

  • Query Store (on by default): a flight recorder of queries, plans and runtime stats — find regressions, force good plans.
  • Automatic tuning: can automatically force last known good plans and (optionally) create/drop indexes.
  • Intelligent Insights / database watcher / Azure Monitor metrics: CPU, data IO, log IO, workers, deadlocks, storage.
  • Resource limits: each tier caps log write throughput and IOPS. Bulk loads from ADF are frequently log-rate-governed — the classic sign is high LOG_RATE_GOVERNOR waits. Mitigations: scale up temporarily for big loads, batch inserts, load into heaps or columnstore, minimise indexes during load.
  • Read scale-out: route reporting or extract queries to the readable secondary (Business Critical/Hyperscale/geo-replicas) with ApplicationIntent=ReadOnly, protecting the primary.

4.7 Azure Cosmos DB (Briefly): The Global Library Network

Analogy: a library chain with branches on every continent. Every branch has a copy of the collection, and you choose how up to date each branch must be before lending a book — "exactly the latest edition everywhere" (slow but perfectly consistent) or "whatever this branch currently has" (fast but possibly slightly behind).

Cosmos DB is a globally distributed NoSQL database (document, key-value, graph, column-family, plus PostgreSQL via Cosmos DB for PostgreSQL). Concepts you should know as a data engineer who extracts from it:

  • Request Units (RU/s): the currency of throughput; every read, write and query costs RUs. Bulk extracts can throttle (HTTP 429) the application if they consume the provisioned RUs.
  • Partition key: decides data distribution — the most important design decision (like a distribution key in MPP).
  • Five consistency levels: Strong, Bounded Staleness, Session (default), Consistent Prefix, Eventual.
  • Change feed: an ordered log of changes per partition — the CDC mechanism for Cosmos DB.
  • Analytical store / Fabric mirroring: replicate operational data into columnar analytics storage without consuming transactional RUs — preferred over large ADF extracts from the transactional store.

Table design — the three distribution choices (seating group-project teams in the same room, from the first guide):

-- Large fact: hash-distribute on a frequently joined, high-cardinality, even key
CREATE TABLE dbo.fact_sales
WITH ( DISTRIBUTION = HASH(customer_sk), CLUSTERED COLUMNSTORE INDEX,
       PARTITION ( date_key RANGE RIGHT FOR VALUES (20240101, 20240201, 20240301) ) )
AS SELECT * FROM stg.sales;

-- Small dimension: copy to every compute node
CREATE TABLE dbo.dim_store
WITH ( DISTRIBUTION = REPLICATE, CLUSTERED INDEX (store_sk) )
AS SELECT * FROM stg.store;

-- Staging: fastest to load, no key needed
CREATE TABLE stg.sales_load
WITH ( DISTRIBUTION = ROUND_ROBIN, HEAP )
AS SELECT * FROM ext.sales_files;

Must-know practices: - CTAS (CREATE TABLE AS SELECT) is the workhorse: fully parallel, minimally logged. Common pattern for big changes: CTAS a new version of the table, then RENAME OBJECT to swap. - Load with COPY INTO (or PolyBase) from ADLS — massively parallel. ADF's copy activity uses these under the hood when you enable them (with staging). - Clustered columnstore needs rows in large compressed row groups (ideally ~1 million rows each); trickle-loading small batches leaves open delta-store row groups. Rebuild indexes periodically. - Don't over-partition: rows are already split across 60 distributions, so each partition × 60 distributions should still hold ~1 million rows per row group. Monthly partitions on a few-billion-row fact may be fine; daily partitions usually aren't. - Statistics must be created/updated (auto-create helps; update after loads). - Workload management: workload groups and classifiers allocate resources and concurrency between ETL and reporting. - Watch data movement (ShuffleMove, BroadcastMove in plans) and skew (DBCC PDW_SHOWSPACEUSED).

6.1 What ADF Is (and Isn't): The Logistics Company

Analogy. ADF is a logistics company. It doesn't own the factories (source systems) or the warehouses (lake, SQL, Synapse), and it doesn't manufacture products itself. It plans routes, dispatches trucks, picks up goods, delivers them, tells the factory to start a production run, and tracks every delivery. When a truck breaks down, it records exactly where and why, and can resend it.

Azure Data Factory is a serverless, cloud-based data integration and orchestration service:

  • It moves data (Copy activity) between 90+ connectors: databases, files, SaaS apps, cloud stores, on-premises systems.
  • It orchestrates work in other services: stored procedures in SQL, notebooks in Databricks, Azure Functions, web APIs, other pipelines.
  • It can transform data visually with Mapping Data Flows (Spark under the hood) — though heavy transformation is usually better done in SQL or Spark engines.
  • It does not store your data (apart from transient staging) — it's the trucks and the dispatch office, not the warehouse.

Analogy: - Parameters are the order form filled in when the job starts ("deliver to: Mumbai, date: 13 Oct"). Variable gotchas: - A Set Variable activity cannot reference the same variable in its expression (@add(variables('counter'),1) into counter is not allowed). The child-pipeline pattern is the robust one. - A pipeline return value (via Set Variable's "pipeline return value" option) lets a child pipeline pass results back to the parent.

6.4 Control Flow Activities: Traffic Lights and Assembly Lines

Dependency Conditions — traffic lights between activities

Analogy: each arrow between activities has a traffic light colour: green (on success), red (on failure), blue (on completion — either way), grey (on skip — the previous activity didn't run).

Condition Next activity runs when previous…
Succeeded succeeded
Failed failed
Completed finished, success or failure
Skipped did not run (because its own dependencies weren't met)

Multiple incoming arrows = AND. If an activity has two incoming dependencies, both must be satisfied. A "send failure email" activity connected with On Failure arrows from three different activities will never run if only one of them fails (the other two succeeded or were skipped).

Patterns: - Try–catch: Activity A → (On Failure) → Log Error → Fail activity (to keep the pipeline marked failed). - Generic error handling for a chain: put the steps in a child pipeline; in the parent, Execute Pipeline → On Failure → handler. One handler covers everything inside. - "Do this whether or not it failed" (e.g., write a log row): use On Completion.

Pipeline Status Logic — why "failed activity, successful pipeline" happens

Analogy: a delivery driver's truck breaks down, he phones the depot (the failure handler), and the depot successfully logs it. The depot's report says "handled successfully", so the day's plan is marked complete — even though the package never arrived.

ADF determines pipeline status from the leaf activities (activities at the end of each path). If a failed activity has an On Failure handler that succeeds, and that handler is the leaf, the pipeline run can report Succeeded. This silently hides failures from monitoring and from parent pipelines.

Fix: end every error-handling path with a Fail activity (custom message and error code), or design so the failure propagates. Then alerts and parent pipelines see the failure correctly.

Lookup — reading the register

Reads a dataset or query result: either the first row or all rows (as an array). Limits (at time of writing): about 5,000 rows and 4 MB of output. It's for control data (config, watermarks), not for moving data. For more rows, page through, or use a stored procedure/query that returns only what you need.

Get Metadata — checking the inbox

Returns properties of a file or folder: exists, childItems (folder contents), lastModified, size, itemName, structure, columnCount. Use it to check whether a file arrived before processing, or to list files for a ForEach.

ForEach — the assembly line

Analogy: an assembly line that processes each item in a list. With sequential mode, one worker handles items one by one. With parallel mode, up to N workers (the batch count) work at once.

  • items: an array expression, e.g., @activity('Lookup Config').output.value.
  • Batch count: default 20, maximum 50 concurrent iterations.
  • Nesting limits: you cannot put a ForEach directly inside another ForEach (or inside If/Switch inside ForEach in some combinations). Use Execute Pipeline to a child that contains the inner loop.
  • Respect source limits: 50 parallel copies against a small on-prem SQL Server can overwhelm it. Tune batch count per source.

If Condition, Switch, Until, Wait, Filter

  • If Condition: two branches based on a boolean expression (@greater(activity('Copy').output.rowsCopied, 0)).
  • Switch: multiple branches on a value (@item().load_type → FULL, INCREMENTAL, CDC).
  • Until: loop until a condition is true, with a timeout — polling an external job's status via Web activity, for example.
  • Wait: pause for N seconds.
  • Filter: filter an array (e.g., keep only .csv files from childItems).

Execute Pipeline — calling a sub-recipe

Calls a child pipeline with parameters. Wait on completion = true makes the parent wait and inherit success/failure. This is how you build modular, reusable frameworks (a generic "copy one table" child called from many parents).

Web / Webhook / Azure Function

  • Web activity: call a REST endpoint (start a Databricks job, call a Logic App, refresh a Power BI dataset, call an internal API). Authenticate with managed identity where supported.
  • Webhook activity: call an endpoint and wait for it to call back (long-running external processes).
  • Azure Function activity: call a function for custom logic.

Validation, Delete, Fail

  • Validation: wait until a file/folder exists (with minimum size, timeout, sleep interval) — a simpler alternative to Until + Get Metadata.
  • Delete: remove files (e.g., clean landing folders after successful load); can log deleted files.
  • Fail: deliberately fail with a custom message and code.

6.5 The Copy Activity in Depth: The Forklift

Analogy: the Copy activity is a forklift team moving pallets from one warehouse to another. You decide how many forklifts (DIUs), how many parallel lanes (parallel copies), whether to use a staging bay (staged copy), how to repack goods (mapping, format conversion), and what to do with damaged pallets (fault tolerance).

Source Options

  • Table, query or stored procedure (for databases). Always prefer a query that selects only needed columns and rows (incremental filters), rather than whole tables.
  • Partition options for parallel reads from relational sources:
  • None — single-threaded read.
  • Physical partitions of table — reads each existing table partition in parallel.
  • Dynamic range — ADF splits a numeric/date column range into chunks and reads them in parallel (?AdfDynamicRangePartitionCondition placeholder in custom queries). Choose an indexed, evenly distributed column.
  • For files: wildcard paths, modifiedDatetimeStart/End filters (incremental by file modified time), recursive folders, "file list path".

Sink Options

  • Write behaviour for SQL sinks: insert, upsert (key columns), or stored procedure. Upsert on large volumes is slower than bulk insert into staging + set-based MERGE.
  • Pre-copy script: e.g., TRUNCATE TABLE staging.sales or DELETE FROM staging.sales WHERE load_date = '@{...}' — key for idempotency.
  • Table option: auto-create table (handy for staging; risky for curated tables because inferred types may be poor).
  • Batch size / write batch timeout.
  • For Synapse/Fabric warehouse sinks: COPY command or PolyBase with staging — dramatically faster than row-by-row bulk insert.

Mapping — repacking the goods

  • Auto mapping by name (convenient, but brittle when sources change).
  • Explicit mapping, which can also be parameterised as JSON from a config table:
{
  "type": "TabularTranslator",
  "mappings": [
    { "source": { "name": "CUST_ID" },   "sink": { "name": "customer_id" } },
    { "source": { "name": "CUST_NAME" }, "sink": { "name": "customer_name" } }
  ]
}

Supply it with @json(item().column_mapping).

  • Type conversion settings control how strings, dates and decimals convert (culture, formats, truncation).

Mapping Data Flows — a factory floor you design on a whiteboard

Analogy: you draw the production line on a whiteboard — "filter out damaged goods, join with the price list, group by store, add a column" — and ADF builds and runs a temporary Spark factory to execute it. You never touch the Spark machinery directly.

The Incremental (Watermark) Pattern, Step by Step

Analogy (from the first guide): a bookmark. Each run reads from the bookmark up to a fixed page, then moves the bookmark — but only after the chapter is safely copied.

  1. Lookup old watermark (first row only): sql SELECT last_value FROM etl.watermark WHERE config_id = @{item().config_id}
  2. Lookup new watermark from the source — fix the upper bound before copying so rows changing mid-copy are caught next run: sql SELECT MAX(@{item().watermark_column}) AS new_value FROM @{item().source_schema}.@{item().source_table}
  3. Copy with a bounded query: sql SELECT @{coalesce(item().select_columns, '*')} FROM @{item().source_schema}.@{item().source_table} WHERE @{item().watermark_column} > '@{activity('Lookup Old WM').output.firstRow.last_value}' AND @{item().watermark_column} <= '@{activity('Lookup New WM').output.firstRow.new_value}' Sink path: @{item().target_folder}/ingest_date=@{formatDateTime(utcNow(),'yyyy-MM-dd')}/@{item().source_table}_@{pipeline().RunId}.parquet
  4. Update watermark via stored procedure, only on success: sql CREATE OR ALTER PROCEDURE etl.usp_update_watermark @config_id INT, @new_value DATETIME2(3), @run_id VARCHAR(64) AS BEGIN SET NOCOUNT ON; UPDATE etl.watermark SET last_value = @new_value, updated_at = SYSUTCDATETIME(), last_run_id = @run_id WHERE config_id = @config_id; END
  5. Audit row counts and status (Section 6.9).

Robustness details (these separate a 3-year engineer from a beginner): - If the copy returns zero rows, new_value from step 2 still advances correctly; if the source table is empty, MAX() returns NULL — guard with coalesce() so the watermark never becomes NULL. - Watermark columns must be indexed in the source; otherwise every incremental run scans the full table. - Add an overlap (e.g., re-read the last hour: > DATEADD(hour,-1, old_value)) when the source's ModifiedDate can be committed late, and deduplicate downstream (by key and latest modified time). - Hard deletes are invisible to this pattern — combine with periodic full key comparison, soft-delete flags, or CDC. - Time zones: be explicit (UTC vs local) about watermark values and when formatting dates into SQL strings; use ISO formats (yyyy-MM-ddTHH:mm:ss.fff). - SQL injection hygiene: config values are concatenated into SQL. Restrict who can edit the control table, validate names (e.g., QUOTENAME in a stored procedure that builds the query), and never take these values from untrusted input.

Other Incremental Options in ADF

  • Tumbling window time ranges instead of stored watermarks (Section 6.2) — great when the source has a reliable modified timestamp and you want built-in backfill.
  • File-based incremental: copy files where lastModified falls within the window (modifiedDatetimeStart/End), or event-driven via storage event triggers.
  • SQL Server / Azure SQL CDC or Change Tracking: query cdc.fn_cdc_get_net_changes_... or CHANGETABLE(CHANGES ...) in the copy source, storing the last LSN/version as the watermark. Captures deletes.
  • ADF's change data capture resource and data flow CDC options, or Fabric mirroring, for lower-code CDC from supported sources.

6.8 Error Handling, Retries and Timeouts

Analogy: a good courier company plans for problems: if a road is temporarily blocked, the driver waits and tries again (retry). If the address doesn't exist, retrying is pointless — report it (fail fast). And no driver should wait at a closed gate forever (timeout).

Activity policy settings: - Retry and retry interval — for transient problems: network blips, throttling (HTTP 429), deadlock victims, serverless database resuming, SHIR momentary disconnect. Typical: 2–3 retries, 30–120 seconds apart. - Timeout — set explicit, realistic timeouts on every activity. Defaults are long (hours or days depending on activity), so a hung query or stuck external job can silently hold the pipeline (and the next scheduled runs) for a very long time. - Secure input / secure output — hides activity inputs/outputs (which may contain secrets or PII) from monitoring logs.

Don't retry logic errors (bad SQL, missing table, permission denied, data type failures) — they fail the same way every time and just delay the alert.

Design patterns: - Fail fast with clear messages: use the Fail activity with a meaningful message ("No file received for POS sales for @{pipeline().parameters.p_date}") and error code. - Centralised error logging: an on-failure/on-completion path that writes pipeline name, run ID, activity, error message (@activity('Copy Sales').error.message) to an audit table. - Restartability: the Monitor hub supports Rerun and Rerun from failed activity. Rerunning safely depends on idempotent design (pre-copy delete/overwrite of the partition, MERGE, watermark only updated on success). - Concurrency control: set the pipeline's concurrency property (e.g., 1) to prevent overlapping runs of the same pipeline processing the same data (a common cause of duplicates when a slow run overlaps the next schedule). Tumbling windows also offer max concurrency and self-dependency.

6.11 Security in ADF

Analogy: a logistics company is trusted with keys to every customer's warehouse. That makes it the most attractive target for burglars. Protect the key cabinet obsessively.

  • Managed identity everywhere possible (ADLS, Azure SQL, Synapse, Key Vault, Databricks, Fabric). Least-privilege roles at the narrowest scope.
  • Secrets only in Key Vault; never inline in linked services or pipeline parameters. Use SecureString parameters and secure input/output to keep secrets and PII out of run logs.
  • Network isolation: Managed Virtual Network + managed private endpoints (approved on the target resource) so the Azure IR reaches storage/SQL without public exposure; Self-hosted IR for on-prem/VNet sources; disable public network access to the factory where appropriate (private endpoint for the ADF portal/authoring and data plane).
  • Customer-managed key encryption for factory metadata if required by policy.
  • RBAC on the factory: Data Factory Contributor for developers in dev only; in prod, deploy via a service connection/managed identity used by CI/CD, with humans as Reader (+ operator rights to rerun if needed).
  • Control the control table: in metadata-driven frameworks, whoever can edit config rows can make the factory read or write arbitrary objects with its powerful identity. Restrict and audit edits.
  • Purview integration for lineage of copy activities, data flows and SSIS.

6.12 Cost Management in ADF: The Courier's Bill

Analogy: the courier charges per dispatch (each activity run), per kilometre-hour of truck usage (data movement), and per hour for specialist crews (data flow clusters, SSIS IR). A thousand tiny parcels cost much more than one well-packed pallet.

ADF billing components (check the current Azure pricing page for rates): - Orchestration: per 1,000 activity runs (including trigger and debug runs). - Data movement: per DIU-hour on Azure IR (cheaper per-hour rates on Self-hosted IR, where you also pay for the VM). - Pipeline/external activity execution time: per hour (e.g., Lookup, Stored Procedure, Databricks activity dispatch). - Data flows: per vCore-hour of cluster time (including debug sessions and TTL warm time). - Azure-SSIS IR: per node-hour while running. - Inactive pipelines carry a small monthly charge.

Cost habits: - Batch work: one copy of 1 GB is cheaper than 10,000 copies of 100 KB. Avoid per-row or per-file ForEach loops over thousands of tiny items where a single folder-level copy works. - Every copy run bills a minimum duration — many tiny copies inflate cost. - Don't over-provision DIUs; let auto decide, then tune with evidence. - Turn off debug clusters; set reasonable TTL for data flows (long TTLs bill idle time). - Stop the Azure-SSIS IR outside job windows. - Avoid aggressive polling (Until loops every 10 seconds for hours) — prefer events/webhooks. - Use tags and separate factories per domain/environment to attribute costs; review Cost Management monthly.

    P -->|invalid| Q[Quarantine folder + alert]

Details: filter the trigger by folder prefix and file suffix (.csv) so temp files don't fire it; use @triggerBody().fileName; validate column count/headers with Get Metadata (structure, columnCount) or a data flow Assert; move processed files to an archive folder and failed files to quarantine; make it idempotent (the same file arriving twice must not double-load — record processed file names and hashes in an audit table).

7.4 Streaming

Event Hubs (partitioned by device or customer ID) → Stream Analytics or Spark Structured Streaming (windowed aggregations, late-arrival handling with watermarks) → Delta tables (silver/gold) and/or real-time dashboards; Event Hubs Capture writes raw events to ADLS for replay. In Fabric: Eventstream → Eventhouse (KQL) / Lakehouse.

Part 8: Operating the platform

8.1 Monitoring Stack: The Building's Control Room

Analogy: a building's control room has screens for CCTV, fire alarms, lifts and power. Each system reports into one place, and the night guard has a runbook for each alarm.

  • Azure Monitor metrics — near-real-time numbers (CPU, DTU, failed runs, storage transactions).
  • Log Analytics workspace — central store for diagnostic logs from ADF, SQL, storage, Databricks, Key Vault; queried with KQL. Use one workspace per environment (or per platform) and set retention per table.
  • Diagnostic settings — must be enabled on each resource to send logs; enforce with Azure Policy so new resources don't slip through.
  • Alerts and Action Groups — who gets notified, how (email, SMS, Teams, ITSM), with severity levels.
  • Workbooks / dashboards — shared operational views (pipeline success rate, durations, data volumes, costs).
  • Azure Service Health — notifications about Azure incidents and planned maintenance affecting your regions — check this before debugging for hours.

8.2 Business Continuity and Disaster Recovery

Analogy (from the first guide): HA is the spare tyre; DR is the second house in another city — and you must actually know the way there before the flood.

Component HA DR approach
ADLS Gen2 ZRS within region GRS/GZRS (async copy to paired region); plan account failover; for logical mistakes rely on soft delete/versioning/snapshots
Azure SQL DB / MI Built-in, zone redundancy Failover groups / geo-replication, geo-restore, LTR backups
Synapse dedicated pool Built-in Geo-backups / restore points to another region
Databricks Cluster resilience Workspace config, notebooks and jobs in Git/IaC; data in geo-redundant storage; secondary workspace
ADF Microsoft-managed service Everything in Git + CI/CD so you can deploy the factory to a secondary region; SHIR nodes in DR site; linked services parameterised for the DR endpoints
Key Vault Built-in redundancy (paired-region replication for many regions) Document recovery; IaC for access configuration

DR runbook essentials: who declares a disaster; order of failover (storage → databases → factories → triggers); switching connection endpoints (failover group listeners help); validating data completeness after failover (what was in flight?); and failing back. Rehearse it at least annually.

8.3 Cost Management: The Household Budget

Analogy: a household budget only works if every expense is categorised, someone looks at it monthly, and there's an alarm when spending runs ahead of plan.

  • Azure Cost Management + Billing: cost analysis by subscription, resource group, service and tag; budgets with alert thresholds (e.g., 50/80/100%); anomaly alerts.
  • Azure Advisor: recommendations (idle resources, right-sizing, reservations).
  • Commitments: reservations and savings plans for steady workloads (SQL vCores, Databricks DBCU pre-purchase, Fabric capacity reservations); Azure Hybrid Benefit for existing SQL Server licences.
  • Usual suspects for runaway costs: all-purpose Databricks clusters left running, Synapse dedicated pools never paused, Azure-SSIS IR running 24/7, data flow debug sessions, oversized SQL tiers, high-frequency polling pipelines, cross-region data egress, uncontrolled Log Analytics ingestion, and storage that never moves to cooler tiers.
  • FinOps habit: a monthly review of top 10 cost drivers with owners, plus "cost per pipeline run" or "cost per TB processed" as tracked metrics.

Part 9: Infrastructure as code

9.1 Why IaC: The Architect's Blueprint

Analogy: a builder who constructs a house from memory will never build two identical houses. With an architect's blueprint, you can build the same house in any city, review changes before construction, and know exactly what's inside every wall.

IaC gives repeatability (dev, test, prod and DR environments are identical by construction), reviewability (pull requests for infrastructure changes), auditability (Git history) and speed (new environment in minutes).

Tools: Bicep (Azure-native, compiles to ARM), Terraform (multi-cloud, azurerm provider), ARM JSON (verbose; mostly generated). ADF's own content (pipelines etc.) is deployed through its ARM-template CI/CD (Part 6.10), while the factory resource, IRs, managed private endpoints, role assignments and diagnostic settings belong in your IaC.

  • ☐ Entra groups for every access level; no individual role assignments; PIM for admin roles

  • ☐ Private endpoints + private DNS for storage, SQL, Key Vault; ADF managed VNet and/or SHIR (2+ nodes)
  • ☐ Diagnostic settings to Log Analytics on every resource; alerts with action groups
  • ☐ Budgets and cost alerts per subscription/resource group
  • ☐ All infrastructure in IaC; ADF Git-integrated in dev with automated CI/CD to test/prod
  • ☐ Backup/restore and DR documented and rehearsed
  • ☐ Purview/Unity Catalog scanning, classification and lineage

10.2 ADF Pipeline Review Checklist

  • ☐ Parameterised datasets and linked services; no hard-coded environment values
  • ☐ Metadata-driven where there are many similar objects
  • ☐ Incremental logic with fixed upper bound, NULL-safe watermark, updated only on success
  • ☐ Idempotent sinks (pre-copy delete/partition overwrite/MERGE)
  • ☐ Explicit timeouts and sensible retries on every activity; no retries on logic errors
  • ☐ Error paths end in a Fail activity; centralised error logging
  • ☐ Pipeline concurrency set to prevent overlapping runs
  • ☐ ForEach batch count tuned to source capacity; no shared variables in parallel loops
  • ☐ Secure input/output on activities handling secrets or PII
  • ☐ Audit row counts written for every load; reconciliation and freshness checks
  • ☐ Alerts on failure and on missed SLA
  • ☐ Cost-aware: no tiny-file loops, no long data flow TTLs, no idle SSIS IR

10.3 Interview Questions with Model Answers

1. Explain linked services, datasets, pipelines, activities, triggers and integration runtimes. Linked service = connection info (where and how to authenticate). Dataset = a named reference to data within that connection (table, file, folder) with format. Activity = one step (copy, lookup, stored procedure). Pipeline = a group of activities with dependencies, parameters and variables. Trigger = what starts a pipeline (schedule, tumbling window, storage/custom event). Integration runtime = the compute that executes activities and moves data (Azure, Self-hosted, Azure-SSIS).

2. Azure IR vs Self-hosted IR — when do you need SHIR? Azure IR is Microsoft-managed and reaches publicly accessible or managed-private-endpoint resources. SHIR is installed on your own machine to reach on-premises or private-network resources; it communicates outbound over HTTPS only. Use 2+ nodes for HA; install Java for Parquet.

3. Schedule vs tumbling window trigger? Schedule fires at clock times, is stateless, can start many pipelines, no backfill. Tumbling window has fixed contiguous windows, 1:1 with a pipeline, passes window start/end, supports backfill, retry, max concurrency and dependencies between windows.

4. How do you build an incremental load in ADF? Control table + watermark table; Lookup old watermark; Lookup new max value (fixed upper bound); Copy with bounded query; update watermark via stored procedure only on success; audit counts. Handle NULLs, late commits (overlap + downstream dedupe), deletes (CDC/soft delete/full key compare), and indexes on the watermark column.

5. What is a metadata-driven pipeline and why use it? One generic set of pipelines driven by config rows (source, target, load type, keys). Adding a table means adding a row, not building a pipeline: consistent, maintainable, testable. Uses Lookup → ForEach → Execute child pipeline with parameters.

6. How do you handle errors so failures aren't hidden? On-failure paths for logging, ending in a Fail activity; or wrap steps in a child pipeline and handle at parent level. Remember pipeline status is based on leaf activities, so a successful handler can mark the pipeline succeeded. Add retries for transient errors, explicit timeouts, alerts via Azure Monitor.

7. How does CI/CD work for ADF? Dev factory connected to Git; feature branches merged via PR to collaboration branch; build validates and exports ARM templates (npm utilities package); release deploys to test/prod with parameter overrides, stopping triggers before and starting after; test/prod never edited manually.

8. How do you secure credentials in ADF? Managed identity wherever possible; otherwise secrets in Key Vault referenced from linked services; SecureString parameters and secure input/output; private networking; least-privilege RBAC.

9. Copy activity is slow. How do you troubleshoot? Read the copy monitoring details: which stage takes time (queue, source read, sink write). Check source query/indexes and partitioning options, SHIR capacity and network, sink throttling (Azure SQL log rate, indexes), file format and size; then tune parallel copies/DIUs; use staging + COPY for Synapse/Fabric.

10. Mapping Data Flows vs Databricks — when to use which? Data flows: visual, managed Spark, good for moderate transformations and teams without Spark skills; cluster start-up and vCore-hour cost. Databricks: code-first, more powerful and optimisable, better for complex/heavy logic, testing and version control. Many teams use ADF for orchestration and ingestion, Databricks or SQL for transformation.

11. What's the difference between ADLS Gen2 and Blob storage? ADLS Gen2 is Blob storage with hierarchical namespace: real directories (atomic rename/delete), POSIX ACLs, and better analytics performance.

12. RBAC vs ACLs on ADLS? RBAC grants broad data-plane rights at container/account scope and is evaluated first; ACLs give folder/file-level rights (r/w/x), need Execute on every parent folder, and default ACLs only apply to new children.

13. Azure SQL Database vs Managed Instance? SQL Database is a single-database PaaS with limited instance features. Managed Instance offers near-full SQL Server compatibility (SQL Agent, cross-database queries, CLR, linked servers) inside your VNet — ideal for lift-and-shift.

14. Synapse dedicated pool distribution types? HASH (large facts on an even, frequently joined key), ROUND_ROBIN (staging, even spread, no key), REPLICATE (small dimensions copied to each compute node). Avoid skew; use clustered columnstore and CTAS; maintain statistics.

15. What is Microsoft Fabric and how does it relate to ADF and Synapse? A SaaS analytics platform with OneLake (Delta storage), Lakehouse, Warehouse, Data Factory pipelines, Dataflow Gen2, real-time analytics and Power BI on shared capacity. It's where Microsoft's new analytics investment is focused; ADF and Synapse remain supported, with migration tooling to Fabric.

16. How do you prevent duplicate data when a pipeline is rerun? Idempotent design: process by window/logical date, pre-copy delete or partition overwrite, MERGE on keys, watermark updated only on success, recording processed files, and pipeline concurrency limits.

17. A parallel ForEach produces wrong results. Why? Pipeline variables are shared across iterations; parallel Set Variable calls race. Use a child pipeline with parameters, Append Variable, or sequential mode.

18. How do you monitor ADF beyond 45 days? Diagnostic settings to Log Analytics (ADFPipelineRun, ADFActivityRun, ADFTriggerRun), KQL queries, workbooks and log alerts; plus your own audit tables.

10.4 Learning Path

  1. Foundations (week 1–2): Azure hierarchy, Entra ID, RBAC, managed identities, Key Vault, networking basics. Build: a resource group with ADLS Gen2, Key Vault and ADF, wired with managed identity.
  2. ADF core (week 3–4): linked services, parameterised datasets, Copy, Lookup, ForEach, triggers, expressions. Build: copy a sample SQL database to Parquet in the lake.
  3. ADF patterns (week 5–6): metadata-driven framework with watermarks, audit table, error handling with Fail activities, tumbling window backfill.
  4. Transformation (week 7–8): Databricks (Delta MERGE, SCD2) or stored-procedure ELT into Azure SQL; orchestrate from ADF.
  5. Operations (week 9): Log Analytics diagnostics, KQL queries, alerts, budgets.
  6. DevOps (week 10): Git integration, automated ARM export, deployment to a second "prod" factory with parameter overrides; Bicep for the infrastructure.
  7. Fabric (ongoing): Lakehouse, Warehouse, Fabric pipelines, shortcuts, mirroring; try migrating one ADF pipeline.
