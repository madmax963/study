    How to Read This Guide

    Every concept follows the same rhythm:

    1. The analogy — a real-world picture so the idea "clicks".
    2. The real explanation — what actually happens inside the database.
    3. Why it matters to you — how it shows up in your daily work or in interviews.
    4. Code or examples — where useful.

    The parts build on each other. Internals (Part 2) explain why indexes work (Part 5), which explains why warehouses are designed differently (Parts 8 and 10). If something later feels confusing, the cause is usually in an earlier part.

    Part 1: The big picture

    1.1 OLTP vs OLAP: The Shop Counter and the Head Office

    Analogy. Picture a large supermarket chain.

    At each checkout counter, cashiers scan items one at a time, take payment, print a receipt, and move to the next customer. Thousands of tiny, fast transactions happen every minute, and every one must be correct. If the till crashes mid-payment, the customer must not be charged twice. That is OLTP (Online Transaction Processing).

    At head office, an analyst asks: "Which product categories grew fastest in the southern region over the last three years, by month?" Nobody is buying anything. She needs to read millions of receipts at once and summarise them. That is OLAP (Online Analytical Processing).

    You could not run head office out of the checkout till. The till is built for speed on one receipt at a time, and if the analyst ran her giant query on it, the queue of customers would stop moving.

    Aspect OLTP (the checkout counter) OLAP (head office)
    Purpose Run the business Understand the business
    Typical operation Insert/update one order Scan and aggregate millions of rows
    Users Applications, thousands of concurrent users Analysts, BI tools, data scientists
    Schema Normalised (3NF) — no duplication Denormalised (star schema) — easy to read
    Storage layout Row-oriented Column-oriented
    Optimised for Low latency, high concurrency, correctness Scan throughput, aggregation
    Data freshness Real-time Minutes to a day old (usually)
    History Current state mostly Years of history
    Examples PostgreSQL, MySQL, SQL Server, Oracle Snowflake, BigQuery, Redshift, Synapse, Databricks

    1.2 Where the Data Engineer Fits: The Logistics Company

    Analogy. If shops are the source systems and head office is the warehouse, the data engineer runs the logistics company in between. You collect goods (data) from hundreds of shops without blocking their aisles, you inspect and clean them, you repackage them into standard boxes, you label them, and you shelve them in the central warehouse so anybody at head office can find what they need. When a truck breaks down at 3 am, you are the one who gets the call.

    Your responsibilities fall into four buckets, which map to the parts of this guide:

    1. Understand the storage engine so you do not hurt source systems and can tune targets.
    2. Model data so it is correct and easy to use.
    3. Move data reliably, repeatably and efficiently.
    4. Operate and protect the platform: security, backup, monitoring, cost.

    Part 2: How a relational database works inside

    2.1 Pages: The Database Never Reads Just One Row

    Analogy. A library stores knowledge in books on shelves. If you need one sentence, you still have to take the whole book off the shelf. You cannot borrow "just line 14 of page 230".

    A database stores rows inside fixed-size blocks called pages (8 KB in PostgreSQL and SQL Server, 16 KB in MySQL InnoDB). A page holds many rows. When you ask for one row, the database reads the entire page that contains it.

    Why it matters: the true cost of a query is not "how many rows did I get back" but "how many pages did the database have to touch". A query returning 10 rows can be slow if those 10 rows are scattered over 10 different pages on disk, while a query returning 1,000 rows can be fast if they sit together on a handful of pages. Every performance concept later in this guide (indexes, clustering, partitioning, columnar storage) is fundamentally about touching fewer pages.

    2.2 Buffer Pool: Your Desk vs the Library Stacks

    Analogy. Walking to the library basement for every book is slow. So you keep the books you use often on your desk. Your desk is small, so when it fills up, you return the book you have not touched for the longest time.

    The buffer pool (SQL Server, MySQL) or shared buffers (PostgreSQL) is the database's desk: a region of RAM holding recently used pages.

    • Logical read = page found on the desk (memory). Fast.
    • Physical read = page fetched from the basement (disk). Slow, often 100x or more.

    Why it matters: the first run of a query is often slower than the second because the cache is "cold". When you benchmark, compare like with like. A server short on memory constantly evicts pages ("desk too small"), and everything gets slower. A huge reporting query run against a production OLTP database can push out all the hot pages the application relies on, slowing the whole application down. This is one reason we extract from replicas.

    2.3 The Write-Ahead Log (WAL): The Chef's Order Ticket

    Analogy. In a busy restaurant, a waiter does not walk into the kitchen and shout the order, hoping the chef remembers. He writes the order on a ticket and pins it to the rail first. If the chef faints halfway through, the next chef reads the tickets and knows exactly what was ordered and what is left to cook. The ticket rail is quick to write to, because you just add a ticket at the end.

    Before the database modifies a data page, it writes a record describing the change to the write-ahead log (called the WAL in PostgreSQL, transaction log in SQL Server, redo log in Oracle/MySQL). The log is written sequentially (always appending at the end), which is very fast. The actual data pages are updated in memory and written to disk later.

    If the server crashes, on restart the database replays the log: redoing committed changes that had not yet reached data files, and undoing uncommitted ones.

    Why it matters to a data engineer, beyond crash recovery:

    • Replication works by shipping the log to another server and replaying it there.
    • Point-in-time recovery works by restoring a backup and replaying the log up to a chosen moment.
    • Change Data Capture (CDC) tools like Debezium, SQL Server CDC and AWS DMS read the log to stream every insert, update and delete to your pipeline.
    • Log growth is a classic outage: a long-running transaction or failing log backups stop the log from being trimmed, the disk fills, and the database stops accepting writes.

    2.4 Checkpoints: Saving Your Game

    Analogy. In a video game, if you never save, a crash sends you back to the very beginning. Saving periodically means you only replay from the last save point.

    A checkpoint flushes dirty (modified) pages from memory to the data files and notes the position in the log. After a crash, recovery only needs to replay the log from the last checkpoint, not from the start of time. Frequent checkpoints mean faster recovery but more background disk writes.

    2.5 ACID: The Four Promises of a Transaction

    A transaction is a group of operations treated as one unit of work. ACID is the set of guarantees a relational database gives about transactions.

    Atomicity — The Vending Machine

    Analogy. You put money into a vending machine. Either you get your snack and the machine keeps the money, or you get your money back. You never lose the money and get no snack.

    All statements in a transaction succeed together or are all rolled back.

    BEGIN;
UPDATE account SET balance = balance - 500 WHERE account_id = 'A';
UPDATE account SET balance = balance + 500 WHERE account_id = 'B';
COMMIT;   -- if anything fails before this, both updates are undone

    Why it matters: your pipeline's "delete yesterday, insert yesterday" step must be inside one transaction. Otherwise a failure between the delete and the insert leaves the report showing zero sales for that day.

    Consistency — The Rules of Chess

    Analogy. In chess, any legal move leaves the board in a legal position. A bishop can never end up on a square of the wrong colour.

    A transaction moves the database from one valid state to another, respecting every declared rule: primary keys, foreign keys, CHECK constraints, NOT NULL. If a statement would break a rule, it fails.

    Isolation — Exam Hall Partitions

    Analogy. Students in an exam hall sit apart so nobody sees anyone else's half-finished answers.

    Concurrent transactions should not see each other's unfinished work. How strictly this is enforced is configurable by isolation level (Section 2.8).

    Durability — Ink, Not Pencil

    Analogy. Once the bank teller stamps and signs your deposit slip, it is in ink. A power cut does not erase it.

    Once the database reports COMMIT, the change survives crashes. This is guaranteed because the log record was flushed to durable storage before commit was acknowledged.

    2.6 Locks: The Petrol Station Bathroom Key

    Analogy. A petrol station bathroom has one key on a big wooden block. Whoever holds the key uses the room; everyone else waits. A notice board, however, can be read by many people at once, but if someone wants to rewrite it, they need everyone else to step back.

    Databases use locks to protect data during changes:

    • Shared lock (S) — "reading the notice board". Many readers can hold it at once.
    • Exclusive lock (X) — "holding the bathroom key". Only one holder; needed to modify.
    • Granularity — locks can be on a row, a page, or a whole table. Row locks allow high concurrency; table locks are cheap to manage but block everyone.
    • Lock escalation (SQL Server) — if one transaction holds thousands of row locks, the engine may convert them into a single table lock to save memory. Suddenly every other user is blocked. A big UPDATE of millions of rows in one statement is a typical trigger, which is why we batch large updates.

    Blocking is when one session waits for another's lock. It is normal for short periods. Long blocking chains (A blocks B, B blocks C, C blocks fifty application sessions) are a production incident.

    2.7 MVCC: Reading Yesterday's Newspaper While Today's Is Being Written

    Analogy. A newspaper's readers read this morning's printed edition. Meanwhile, in the newsroom, editors are writing tomorrow's edition. The readers are never blocked by the editors, and the editors are never blocked by the readers. Each reader sees one complete, consistent edition, never a half-edited page.

    Multi-Version Concurrency Control (MVCC) keeps multiple versions of a row. When a row is updated, the old version is kept for any transaction that started earlier and still needs to see it. Readers see a consistent snapshot as of when their statement (or transaction) began.

    • PostgreSQL stores old versions in the table itself (dead tuples), cleaned later by VACUUM.
    • Oracle and MySQL InnoDB keep old versions in undo segments.
    • SQL Server uses locking by default but offers MVCC via Read Committed Snapshot Isolation (RCSI) and Snapshot Isolation, storing versions in tempdb.

    Key rule: in MVCC, readers do not block writers and writers do not block readers. Writers still block other writers on the same row.

    The cost: old versions pile up like old newspapers. They must be recycled (vacuum / version cleanup). A transaction left open for hours prevents cleanup, causing table bloat in PostgreSQL or tempdb growth in SQL Server.

    2.8 Isolation Levels and Anomalies: What Can Go Wrong When Two People Work at Once

    First, the anomalies, each with a picture.

    Dirty read — reading a draft email.

    Your colleague types "The project is cancelled" in a draft, you glance at her screen and tell the whole team, then she deletes the draft. You acted on something that never officially existed.

    Transaction B reads a change made by A that A has not committed (and may roll back).

    Non-repeatable read — the price changed between glances.

    You check the price of a flight: ₹5,000. You check again two minutes later in the same browsing session: ₹6,200. The same row gave two different answers.

    Within one transaction, re-reading the same row returns different data because someone else committed an update in between.

    Phantom read — counting people in a room with an open door.

    You count 20 people in a room. While you are writing the number down, three more walk in. You count again: 23. No individual person changed, but the set changed.

    Re-running the same range query returns new rows that another transaction inserted.

    Lost update — two people editing the same offline spreadsheet.

    Asha and Ravi both download the stock spreadsheet showing 100 units. Asha sells 10 and uploads "90". Ravi sells 5 and uploads "95". Asha's sale vanished.

    Two transactions read, modify and write the same value; the second overwrites the first.

    Write skew — two doctors going off call.

    Rule: at least one doctor must be on call. Two doctors are on call. Each checks "is someone else on call? Yes," and each signs off. Now nobody is on call. Neither transaction changed the same row, yet together they broke the rule.

    Isolation level Dirty read Non-repeatable read Phantom Notes
    Read Uncommitted Possible Possible Possible NOLOCK in SQL Server; avoid for anything important
    Read Committed Prevented Possible Possible Default in PostgreSQL, SQL Server, Oracle
    Repeatable Read Prevented Prevented Possible (by standard) Default in MySQL; PostgreSQL's version also prevents phantoms
    Serializable Prevented Prevented Prevented Also prevents write skew; slowest, may raise serialization errors you must retry

    Fixing lost updates in practice:

    -- 1. Atomic update: let the database do the arithmetic
UPDATE stock SET qty = qty - 10 WHERE product_id = 42;

-- 2. Pessimistic lock: lock the row while you decide
BEGIN;
SELECT qty FROM stock WHERE product_id = 42 FOR UPDATE;
-- application logic
UPDATE stock SET qty = 90 WHERE product_id = 42;
COMMIT;

-- 3. Optimistic lock: version column
UPDATE stock SET qty = 90, version = version + 1
WHERE product_id = 42 AND version = 7;   -- 0 rows updated = someone else got there first; retry

    Why isolation matters to a data engineer: suppose you extract orders at 01:00 and order_lines at 01:20, both under Read Committed. Orders placed between 01:00 and 01:20 have lines but no header in your extract, and your join drops them or your foreign-key test fails. Solutions: extract from a consistent snapshot (a replica paused at a point, a database snapshot, a single transaction under snapshot/repeatable read isolation), or use CDC with consistent log positions.

    NOLOCK warning: many SQL Server scripts use WITH (NOLOCK) to "avoid blocking". It is Read Uncommitted: you can read rows twice, skip rows, or read rolled-back data. For pipelines that must be correct, prefer RCSI/snapshot isolation instead.

    2.9 Deadlocks: Two Cars on a Single-Lane Bridge

    Analogy. Two cars enter a single-lane bridge from opposite ends and meet in the middle. Neither can move forward, neither will reverse. Someone has to be told to back up.

    Or: two diners at a table with only two chopsticks. Each grabs one and waits for the other to release theirs. Nobody eats.

    Transaction A locks row 1 and wants row 2. Transaction B locks row 2 and wants row 1. Neither can proceed. The database's deadlock detector picks a victim, rolls it back, and returns an error (SQL Server error 1205, PostgreSQL "deadlock detected").

    Prevention:

    1. Access objects in the same order everywhere (everyone enters the bridge from the north side).
    2. Keep transactions short; never wait for user input or an API call inside a transaction.
    3. Index foreign keys and filter columns so updates lock only the rows they need, not large ranges.
    4. Use MVCC-based isolation to remove reader/writer deadlocks.
    5. Retry on deadlock in your pipeline code; a deadlock victim usually succeeds on retry.

    Part 3: Relational data modelling (OLTP design)

    3.1 Why Normalise? The Address Written on Every Letter

    Analogy. Imagine you keep a copy of every letter you have ever sent, and you write your full home address at the top of each one. You move house. Now you must find and correct hundreds of letters, and if you miss one, you have two "true" addresses. That is an update anomaly.

    The fix: keep your address in one place (your address book card) and have each letter just say "From: me". Change the card once and every letter is correct.

    Normalisation organises tables so each fact is stored exactly once. It prevents three anomalies:

    • Update anomaly — changing a fact requires changing many rows.
    • Insert anomaly — you cannot record a fact without some unrelated fact (you cannot add a new product until someone orders it, because products only live inside the orders table).
    • Delete anomaly — deleting one thing accidentally deletes another (deleting the last order of a product erases the product's existence).

    The Normal Forms, Step by Step

    Start with this messy table:

    order_id customer_name customer_city products product_prices
    1 Priya Mumbai Pen, Notebook 20, 50
    2 Priya Mumbai Pen 20

    First Normal Form (1NF) — one item per drawer.

    Analogy: a cutlery drawer with separate slots: forks in one slot, spoons in another. You never jam "two forks and a spoon" into one slot.

    Every column holds a single atomic value; no lists, no repeating groups.

    order_id line_no customer_name customer_city product price
    1 1 Priya Mumbai Pen 20
    1 2 Priya Mumbai Notebook 50
    2 1 Priya Mumbai Pen 20

    Second Normal Form (2NF) — every column depends on the whole key. The key here is (order_id, line_no). But customer_name depends only on order_id, and price depends only on product. These are partial dependencies. Split them out: an orders table (order_id → customer), an order_line table (order_id, line_no → product, quantity), and a product table (product → price).

    Third Normal Form (3NF) — no column depends on another non-key column. In orders, if we store both customer_id and customer_city, then city depends on customer, not on the order. That is a transitive dependency. Move city into the customer table.

    The memory rule (Bill Kent's): every non-key column must depend on the key, the whole key, and nothing but the key.

    Boyce-Codd Normal Form (BCNF) is a stricter 3NF: every column that determines another must be a candidate key. In practice, aim for 3NF in OLTP; BCNF issues are rare.

    Result:

    erDiagram
    CUSTOMER ||--o{ ORDERS : places
    ORDERS ||--|{ ORDER_LINE : contains
    PRODUCT ||--o{ ORDER_LINE : "appears in"
    CUSTOMER {
        bigint customer_id PK
        string name
        string city
    }
    ORDERS {
        bigint order_id PK
        bigint customer_id FK
        timestamp order_ts
    }
    ORDER_LINE {
        bigint order_id PK
        int line_no PK
        bigint product_id FK
        int quantity
        decimal unit_price
    }
    PRODUCT {
        bigint product_id PK
        string name
        decimal list_price
    }

    Note unit_price is kept on order_line even though product has list_price. This is not a normalisation mistake: the price at the time of sale is a different fact from today's list price. Recognising "different facts that look the same" is a key modelling skill.

    Denormalisation — Pre-Packed Lunch Boxes

    Analogy. A school canteen could cook every meal to order from raw ingredients (normalised), or prepare packed lunch boxes in advance (denormalised). Lunch boxes are much faster to hand out, but if the recipe changes, every box must be repacked.

    Denormalisation deliberately duplicates data for faster reads. It is the norm in warehouses (Part 8) and used selectively in OLTP (e.g., storing order_total on the order header). The price: you must keep the copies in sync.

    3.2 Keys: Name Tags, Roll Numbers and Badges

    Analogy. In a school, a student's name identifies them, but two students may share a name, and names can change. So the school issues a roll number: unique, never reused, meaningless on its own, never changes.

    • Natural key (business key): an identifier with real-world meaning — email, PAN, product SKU, employee code. Meaningful, but may change, be reused, be long, or be formatted inconsistently across systems.
    • Surrogate key: a system-generated value (identity integer, sequence, UUID) with no business meaning. Stable, compact, fast to join.
    • Composite key: made of multiple columns, e.g., (order_id, line_no).
    • Candidate key: any column set that could uniquely identify a row. You pick one as the primary key; protect the others with UNIQUE constraints so the business rule is still enforced.

    Integer vs UUID primary keys:

    Analogy: adding new pages to the end of a binder is easy (sequential integers). Inserting each new page at a random place in the binder means constantly opening the binder in the middle, shifting pages, and splitting full sections (random UUIDs).

    Random UUIDs as a clustered key cause page splits and fragmentation. If you need globally unique IDs, use time-ordered UUIDs (UUIDv7, NEWSEQUENTIALID() in SQL Server) or keep the UUID as a non-clustered unique column.

    Overflow danger: INT maxes out at about 2.1 billion. Many real outages are "the ID column ran out". Use BIGINT for any table that can grow large.

    3.3 Constraints: The Bouncer at the Door

    Analogy. A nightclub bouncer checks every guest at the door. It is much easier to stop a problem entering than to find and remove it from a packed dance floor later.

    Constraints stop bad data at insert time:

    CREATE TABLE customer (
    customer_id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email         VARCHAR(255) NOT NULL UNIQUE,
    full_name     VARCHAR(200) NOT NULL,
    status        VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE'
                  CHECK (status IN ('ACTIVE','SUSPENDED','CLOSED')),
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    order_id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id   BIGINT NOT NULL REFERENCES customer(customer_id),
    order_ts      TIMESTAMPTZ NOT NULL,
    total_amount  NUMERIC(12,2) NOT NULL CHECK (total_amount >= 0)
);

-- Always index foreign key columns
CREATE INDEX ix_orders_customer_id ON orders(customer_id);
    Constraint Protects against
    PRIMARY KEY Duplicate or missing identity
    UNIQUE Duplicate business keys (two customers with one email)
    NOT NULL Missing mandatory values
    CHECK Invalid values (negative amounts, unknown statuses)
    FOREIGN KEY Orphan rows (an order for a customer who does not exist)
    DEFAULT Missing values where a sensible default exists

    Why index foreign keys? When you delete a customer, the database must check orders for children. Without an index on orders.customer_id, that is a full scan of orders, and it takes broad locks, a frequent deadlock cause.

    In warehouses: Snowflake, BigQuery, Redshift and Synapse accept PK/FK declarations but do not enforce them (they are hints for the optimiser). Your pipeline and data tests must do the bouncer's job (Part 11).

    3.4 Data Types: Choosing the Right Container

    Analogy. You would not store soup in a paper bag or carry a single coin in a suitcase. The container should fit the contents exactly.

    Money: use DECIMAL/NUMERIC(p,s), never FLOAT.

    Analogy: FLOAT is like measuring with a slightly stretchy tape measure. Fine for estimating a room size, unacceptable for counting rupees. 0.1 + 0.2 in floating point is 0.30000000000000004. Over millions of rows, reports stop reconciling.

    Dates and times: use real DATE/TIMESTAMP types, never strings. Store timestamps in UTC with time-zone awareness (TIMESTAMPTZ, DATETIMEOFFSET), convert to local time only for display. Daylight-saving changes and multi-country operations break naive local timestamps (a "missing hour" or "duplicate hour" each year).

    Strings: size them sensibly. Oversized VARCHAR(MAX)/TEXT columns can't always be indexed and inflate memory grants. Know your collation (case sensitivity, accent sensitivity) because it changes comparisons and joins.

    Join column types must match. Joining VARCHAR to INT, or VARCHAR to NVARCHAR in SQL Server, forces an implicit conversion on every row, which can make the index unusable (Section 5.5).

    Booleans and enums: use BOOLEAN/BIT or a small code with a CHECK constraint, rather than free text like "Y", "yes", "TRUE", "1".

    3.5 Relationship Patterns

    • One-to-many (customer → orders): foreign key on the "many" side.
    • Many-to-many (students ↔ courses): a junction table.

      Analogy: the enrolment register. Students don't store a list of courses, and courses don't store a list of students. The register has one line per (student, course) pair, plus facts about the enrolment like date and grade.

    • One-to-one (user → user_profile): same primary key in both tables; used to split rarely used or sensitive columns.
    • Self-referencing hierarchy (employee → manager, category → parent category): a foreign key pointing to the same table. Query with recursive CTEs (Section 4.6).
    • Soft deletes: a deleted_at column instead of physically deleting rows. Every query, unique constraint and report must account for it; partial unique indexes help (CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL). For a data engineer, soft deletes are good news: hard deletes are invisible to timestamp-based incremental loads (Section 9.2).

    Part 4: SQL mastery

    4.1 Logical Order of Execution: Following a Recipe

    Analogy: cooking a dish. 1. FROM / JOIN — fetch all the ingredients from the fridge and pantry and put them on the counter. 2. WHERE — throw away what's spoiled or not needed. 3. GROUP BY — sort what's left into bowls (all onions in one bowl, all tomatoes in another). 4. HAVING — discard bowls that are too small to bother with. 5. SELECT — chop, mix, and prepare what goes on the plate (and compare each portion with its neighbours — window functions happen here). 6. DISTINCT — remove identical plates. 7. ORDER BY — line the plates up in order. 8. LIMIT / TOP — serve only the first few.

    You write SQL in the order SELECT … FROM … WHERE …, but the engine logically processes it in the order above. This explains common errors:

    • You cannot use a SELECT alias in WHERE — the alias doesn't exist yet when WHERE runs. You can use it in ORDER BY.
    • You cannot use an aggregate in WHERE — groups don't exist yet. Use HAVING.
    • You cannot filter on a window function in WHERE — it is computed in step 5. Wrap it in a CTE or subquery, or use QUALIFY (Snowflake, BigQuery, Databricks, Teradata).
    -- Fails: window function in WHERE
SELECT * FROM orders WHERE ROW_NUMBER() OVER (ORDER BY order_ts) = 1;

-- Works everywhere
WITH x AS (SELECT o.*, ROW_NUMBER() OVER (ORDER BY order_ts) AS rn FROM orders o)
SELECT * FROM x WHERE rn = 1;

-- Works in Snowflake / BigQuery / Databricks
SELECT * FROM orders QUALIFY ROW_NUMBER() OVER (ORDER BY order_ts) = 1;

    (The optimiser may physically reorder steps for speed, but the results must match this logical order.)

    4.2 Joins: The Class Roster and the Homework Pile

    Analogy. A teacher has a class roster (left table) and a pile of submitted homework (right table).

    • INNER JOIN: list only students who submitted homework.
    • LEFT JOIN: list every student on the roster; next to those who didn't submit, write "—" (NULL).
    • RIGHT JOIN: list every piece of homework, even ones with no matching student on the roster (a transfer student, a typo in a name).
    • FULL OUTER JOIN: everyone and everything, matched where possible.
    • CROSS JOIN: pair every student with every homework sheet (rarely what you want, except to generate combinations like every store × every date).
    • SEMI JOIN (EXISTS): "which students submitted something?" — each student listed once, no matter how many sheets.
    • ANTI JOIN (NOT EXISTS): "which students submitted nothing?" — the list for detention.
    Join Keeps from left Keeps from right Duplicates left rows?
    INNER matched only matched only yes, if multiple matches
    LEFT all matched only yes, if multiple matches
    FULL all all yes
    SEMI (EXISTS / IN) matched only none (just tests) no
    ANTI (NOT EXISTS) unmatched only none no

    The LEFT JOIN + WHERE Trap

    -- WRONG: students with no 2024 homework disappear
SELECT s.student_id, h.homework_id
FROM student s
LEFT JOIN homework h ON h.student_id = s.student_id
WHERE h.submitted_on >= '2024-01-01';

    Students who submitted nothing have h.submitted_on = NULL, and NULL >= '2024-01-01' is not true, so WHERE removes them. Your LEFT JOIN silently became an INNER JOIN.

    -- RIGHT: put conditions on the right table in the ON clause
SELECT s.student_id, h.homework_id
FROM student s
LEFT JOIN homework h
  ON h.student_id = s.student_id
 AND h.submitted_on >= '2024-01-01';

    Rule: filters on the preserved (left) table go in WHERE; filters on the optional (right) table go in ON.

    Join Fan-Out: The Photocopier Problem

    Analogy. You have one invoice for ₹10,000 and you staple it to each of its 3 delivery notes. Now you have 3 stapled bundles, and if you sum the invoice amount across bundles you get ₹30,000.

    When you join a table to another with multiple matching rows per key, rows multiply. Summing a measure from the "one" side then double or triple counts.

    -- Order header has total_amount; joining to lines multiplies it
SELECT SUM(o.total_amount)          -- inflated!
FROM orders o JOIN order_line l ON l.order_id = o.order_id;

    Defences: know the grain (what one row represents) of every table before joining; aggregate the many-side first, then join; and compare row counts before and after each join while developing.

    4.3 NULL: The Sealed Envelope

    Analogy. NULL is a sealed envelope whose contents are unknown. Is the envelope's content equal to 5? Unknown. Is it equal to another sealed envelope? Also unknown — they might hold the same thing or not. NULL is not zero and not an empty string; it is "unknown / not applicable".

    SQL uses three-valued logic: TRUE, FALSE and UNKNOWN. WHERE keeps only TRUE rows, so UNKNOWN rows are silently dropped.

    Expression Result
    NULL = NULL UNKNOWN (use IS NULL or IS NOT DISTINCT FROM)
    NULL <> 'CLOSED' UNKNOWN → row dropped by WHERE status <> 'CLOSED'
    NULL + 10 NULL
    COUNT(*) counts all rows
    COUNT(col) counts non-NULL values only
    AVG(col) over (10, NULL, 20) 15, not 10 — NULL is ignored, not treated as 0
    TRUE OR NULL TRUE
    FALSE AND NULL FALSE

    The NOT IN Trap

    -- Returns ZERO rows if any orders.customer_id is NULL
SELECT * FROM customer
WHERE customer_id NOT IN (SELECT customer_id FROM orders);

    Why? x NOT IN (1, 2, NULL) means x <> 1 AND x <> 2 AND x <> NULL. The last part is UNKNOWN, so the whole thing can never be TRUE.

    -- Always safe
SELECT * FROM customer c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

    Habits: use COALESCE(col, default) deliberately; when comparing for change detection, use IS DISTINCT FROM (PostgreSQL, Snowflake, Databricks) or wrap both sides in COALESCE; remember NULLs in join keys never match.

    4.4 Aggregation: The Ballot Count

    Analogy: on election night, officials sort ballots into piles by constituency (GROUP BY), count each pile (COUNT/SUM), and only announce constituencies where turnout exceeded a threshold (HAVING).

    -- Conditional aggregation: a pivot without PIVOT syntax
SELECT
    customer_id,
    SUM(CASE WHEN channel = 'WEB'   THEN amount ELSE 0 END) AS web_sales,
    SUM(CASE WHEN channel = 'STORE' THEN amount ELSE 0 END) AS store_sales,
    COUNT(DISTINCT order_id)                               AS order_count,
    COUNT(*) FILTER (WHERE amount > 1000)                  AS big_orders   -- PostgreSQL syntax
FROM sales
GROUP BY customer_id
HAVING SUM(amount) > 1000;

    Subtotals in one pass:

    SELECT region, category, SUM(amount) AS sales,
       GROUPING(region) AS is_region_total, GROUPING(category) AS is_cat_total
FROM sales
GROUP BY ROLLUP (region, category);
-- ROLLUP(a,b) gives (a,b), (a), () — a hierarchy of subtotals
-- CUBE(a,b) gives every combination: (a,b), (a), (b), ()
-- GROUPING SETS ((a),(b)) gives exactly the sets you list

    COUNT(DISTINCT) is expensive on huge data (it must remember every distinct value). Warehouses offer approximate versions (APPROX_COUNT_DISTINCT, HyperLogLog) that are ~1–2% off but vastly cheaper; fine for dashboards, not for finance.

    4.5 Window Functions: Looking Out of the Window Without Leaving Your Seat

    Analogy. GROUP BY is a blender: you put in 100 strawberries and get one smoothie. You lose the individual strawberries.

    A window function is like each passenger on a train looking out of the window: every passenger stays in their own seat (every row is kept), but each can see and compare with the passengers around them — "how do I rank against everyone in my carriage?", "who sat in front of me?", "what's the running total of tickets sold so far in this carriage?".

    Syntax anatomy:

    function() OVER (
    PARTITION BY ...   -- which "carriage" (group) to look within
    ORDER BY ...       -- the order of seats in the carriage
    ROWS BETWEEN ...   -- how far you can see (the frame)
)

    SELECT
    customer_id, order_id, order_ts, amount,

    -- Ranking
    ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_ts)  AS order_seq,
    RANK()       OVER (ORDER BY amount DESC)                        AS rnk,      -- 1,2,2,4
    DENSE_RANK() OVER (ORDER BY amount DESC)                        AS drnk,     -- 1,2,2,3
    NTILE(4)     OVER (ORDER BY amount DESC)                        AS quartile,

    -- Looking at neighbours
    LAG(amount)  OVER (PARTITION BY customer_id ORDER BY order_ts)  AS prev_amount,
    LEAD(order_ts) OVER (PARTITION BY customer_id ORDER BY order_ts) AS next_order_ts,
    FIRST_VALUE(order_ts) OVER (PARTITION BY customer_id ORDER BY order_ts) AS first_order_ts,

    -- Running and moving calculations
    SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_ts
                      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
    AVG(amount) OVER (PARTITION BY customer_id ORDER BY order_ts
                      ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS moving_avg_7,

    -- Share of total
    amount * 1.0 / SUM(amount) OVER (PARTITION BY customer_id)      AS pct_of_customer
FROM orders;

    Ranking Functions Explained with a Race

    Four runners finish: Anu 10.1s, Ben 10.3s, Chen 10.3s, Dev 10.8s.

    Runner ROW_NUMBER RANK DENSE_RANK
    Anu 1 1 1
    Ben 2 2 2
    Chen 3 2 2
    Dev 4 4 3

    ROW_NUMBER breaks ties arbitrarily (add a tie-breaker column to ORDER BY to make it deterministic!). RANK leaves gaps after ties, like the Olympics (no bronze if two share silver). DENSE_RANK never leaves gaps.

    Frames: ROWS vs RANGE

    Analogy: ROWS counts seats ("the 3 seats behind me"). RANGE counts by value ("everyone who boarded at the same station or earlier").

    Important trap: when you write ORDER BY without a frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. If two rows have the same order_ts, they are "peers" and both get the same running total, which includes both rows. Running totals look like they "jump". Always specify ROWS explicitly for running totals.

    4.6 CTEs: Labelled Prep Bowls

    Analogy: a chef preps ingredients into labelled bowls — "diced onions", "marinated chicken" — before cooking. The final recipe says "combine the marinated chicken with the diced onions", which is far easier to read than one enormous instruction.

    A Common Table Expression (CTE) names an intermediate result.

    WITH recent_orders AS (
    SELECT * FROM orders WHERE order_ts >= CURRENT_DATE - INTERVAL '90 days'
),
customer_totals AS (
    SELECT customer_id, SUM(total_amount) AS total_90d, COUNT(*) AS orders_90d
    FROM recent_orders GROUP BY customer_id
)
SELECT c.full_name, t.total_90d, t.orders_90d
FROM customer_totals t JOIN customer c USING (customer_id)
WHERE t.total_90d > 500;

    Performance note: CTEs are mostly for readability. Some engines inline them (PostgreSQL 12+ by default), some may materialise them. A CTE referenced many times may be recomputed each time; if it's expensive, consider a temp table.

    Temp tables vs CTEs vs subqueries: temp tables persist for the session, can be indexed and have statistics, which helps the optimiser on multi-step heavy logic. CTEs and subqueries are just part of one query.

    Recursive CTEs: Climbing the Family Tree

    Analogy: to list all descendants of a grandmother, you start with her (the anchor), then repeatedly ask "who are the children of the people I found in the last step?" (the recursive step) until no new people appear.

    WITH RECURSIVE org AS (
    -- Anchor: the CEO
    SELECT employee_id, manager_id, name, 1 AS lvl,
           CAST(name AS VARCHAR(1000)) AS path
    FROM employee WHERE manager_id IS NULL
    UNION ALL
    -- Recursive step: direct reports of the previous level
    SELECT e.employee_id, e.manager_id, e.name, o.lvl + 1,
           CAST(o.path || ' > ' || e.name AS VARCHAR(1000))
    FROM employee e
    JOIN org o ON e.manager_id = o.employee_id
)
SELECT * FROM org ORDER BY path;

    Guard against cycles (bad data where A manages B and B manages A) with a level limit (WHERE o.lvl < 20) or SQL Server's MAXRECURSION.

    4.7 Must-Know Patterns

    Deduplication: Keeping the Latest Version of a Document

    Analogy: a folder contains "report_v1", "report_v2", "report_final", "report_final_FINAL". You sort each document's versions by date and keep only the newest.

    WITH ranked AS (
    SELECT s.*,
           ROW_NUMBER() OVER (PARTITION BY customer_id
                              ORDER BY updated_at DESC, _ingested_at DESC) AS rn
    FROM stg_customer s
)
SELECT * FROM ranked WHERE rn = 1;

    Always include a tie-breaker in ORDER BY; otherwise identical timestamps give non-deterministic results that change between runs.

    Top N per Group

    Same pattern with WHERE rn <= 3 ("top 3 products per category"). Use DENSE_RANK if ties should all be included.

    Gaps and Islands: The Attendance Streak

    Analogy. A gym tracks members' visit days. "What's each member's longest streak of consecutive days?" Consecutive days are an island; missing days are gaps.

    The trick: number the visits 1, 2, 3, … in date order and subtract that number from the date. For consecutive days, both the date and the counter go up by 1, so the difference stays constant. When there is a gap, the date jumps but the counter doesn't, so the difference changes. Each constant difference = one island.

    visit_date row_number date − row_number
    Oct 1 1 Sep 30
    Oct 2 2 Sep 30
    Oct 3 3 Sep 30
    Oct 6 4 Oct 2
    Oct 7 5 Oct 2 
    WITH d AS (SELECT DISTINCT member_id, visit_date FROM gym_visits),
g AS (
    SELECT member_id, visit_date,
           visit_date - CAST(ROW_NUMBER() OVER (PARTITION BY member_id ORDER BY visit_date) AS INT) AS grp
    FROM d
)
SELECT member_id, MIN(visit_date) AS streak_start, MAX(visit_date) AS streak_end, COUNT(*) AS days
FROM g
GROUP BY member_id, grp
ORDER BY days DESC;

    (In SQL Server use DATEADD(day, -ROW_NUMBER() OVER (...), visit_date).)

    Upsert / MERGE: Syncing Your Phone Contacts

    Analogy: you import a new contact list into your phone. For people already in your phone, update their numbers if changed; for new people, add them; optionally, delete contacts not in the new list.

    -- PostgreSQL
INSERT INTO dim_product (product_code, name, price)
SELECT product_code, name, price FROM stg_product
ON CONFLICT (product_code)
DO UPDATE SET name = EXCLUDED.name, price = EXCLUDED.price
WHERE dim_product.name IS DISTINCT FROM EXCLUDED.name
   OR dim_product.price IS DISTINCT FROM EXCLUDED.price;

-- SQL Server / Snowflake / Oracle / Databricks
MERGE INTO dim_product t
USING stg_product s
   ON t.product_code = s.product_code
WHEN MATCHED AND (t.name <> s.name OR t.price <> s.price) THEN
    UPDATE SET name = s.name, price = s.price
WHEN NOT MATCHED THEN
    INSERT (product_code, name, price) VALUES (s.product_code, s.name, s.price);

    MERGE pitfalls: the source must have one row per key (deduplicate first, or MERGE errors or behaves unpredictably); the <> comparison misses NULL changes (use IS DISTINCT FROM or hash comparison); in SQL Server, MERGE has known concurrency edge cases, so use HOLDLOCK or separate UPDATE/INSERT statements for high-concurrency tables.

    Date Spine: Filling Missing Days

    Analogy: a calendar on the wall shows every day even if you did nothing that day. Reports need the same: "zero sales" days must appear as zero, not vanish.

    WITH days AS (
    SELECT generate_series(DATE '2024-10-01', DATE '2024-10-31', INTERVAL '1 day')::date AS d
)
SELECT days.d, COALESCE(SUM(s.amount), 0) AS sales
FROM days
LEFT JOIN sales s ON s.sale_date = days.d
GROUP BY days.d ORDER BY days.d;

    In practice, join to a permanent dim_date table instead.

    Set Operations: Reconciliation's Best Friend

    UNION removes duplicates (costs a sort/hash); UNION ALL keeps everything (faster — use it by default). EXCEPT (MINUS in Oracle) returns rows in A not in B; INTERSECT returns rows in both.

    -- Rows in source but missing/different in target
SELECT customer_id, email, region FROM src_customer
EXCEPT
SELECT customer_id, email, region FROM dim_customer WHERE is_current;

    4.8 Views, Materialised Views, Procedures, Functions, Triggers

    • View — a window: you look through it at the live data behind it. It stores no data; it's a saved query. Great for security (expose only some columns) and simplification.
    • Materialised view — a photograph: a stored copy of the result at one moment. Fast to read, but it goes stale until refreshed. Some warehouses refresh automatically/incrementally (Snowflake, BigQuery); others need explicit REFRESH MATERIALIZED VIEW.
    • Stored procedure — a saved recipe card with steps, variables, loops and error handling. Common for ELT orchestration in SQL Server/Synapse.
    • Function — returns a value or table. Beware scalar UDFs in SQL Server (pre-2019) that run once per row and prevent parallelism.
    • Trigger — a motion-sensor light: it runs automatically when an INSERT/UPDATE/DELETE happens. Useful for audit trails, but hidden logic surprises people, slows writes, and complicates bulk loads. Use sparingly.

    Part 5: Indexing and query performance

    5.1 What an Index Is: The Index at the Back of a Textbook

    Analogy. To find every mention of "photosynthesis" in a 600-page biology textbook, you could read all 600 pages (a full table scan), or turn to the index at the back, which lists "photosynthesis — pages 45, 112, 310". You jump straight to those pages (an index seek).

    An index is a separate, sorted structure that maps column values to the location of rows. It trades extra storage and slower writes for much faster reads.

    5.2 B-Tree: The Dictionary's Guide Words

    Analogy. A paper dictionary shows guide words at the top of each page ("mango — marble"). You open near the middle, see "lemon", know "mango" is later, flip forward, and within a few jumps you're on the right page. You never read every word.

    Or think of postal addressing: country → state → city → street → house. Each level narrows the search drastically.

    A B-tree (balanced tree) index has:

    • A root page at the top with ranges pointing to the next level.
    • Intermediate (branch) pages narrowing the range further.
    • Leaf pages at the bottom holding the sorted key values plus pointers to rows. Leaf pages are linked to their neighbours, so range scans just walk sideways.
    flowchart TB
    R["Root: 1–500 | 501–1000"] --> B1["Branch: 1–250 | 251–500"]
    R --> B2["Branch: 501–750 | 751–1000"]
    B1 --> L1["Leaf: 1…125"]
    B1 --> L2["Leaf: 126…250"]
    B2 --> L3["Leaf: 501…625"]
    B2 --> L4["Leaf: 626…750"]
    L1 <--> L2
    L3 <--> L4

    Because each page holds hundreds of entries, even a billion-row table usually needs only 3–5 levels. A lookup is 3–5 page reads instead of millions. B-trees support =, <, >, BETWEEN, LIKE 'abc%' (prefix) and ORDER BY on the indexed columns.

    5.3 Clustered vs Non-Clustered Indexes

    Analogy. - A clustered index is like a dictionary itself: the words (rows) are physically printed in alphabetical order. There can be only one physical order, so a table has at most one clustered index. - A non-clustered index is like the index at the back of a textbook: a separate list pointing to page numbers. You can have many such indexes (by topic, by author, by figure).

    • SQL Server / MySQL InnoDB: the table is stored in clustered-index order (InnoDB always clusters on the primary key). Non-clustered indexes store the clustered key as their "pointer".
    • PostgreSQL: tables are heaps (no inherent order); all indexes are secondary and point to physical row locations. (CLUSTER reorders once but doesn't maintain the order.)

    Choosing a clustered key (SQL Server): narrow, unique, static (never updated), and ever-increasing (e.g., an identity BIGINT or a date + id). Why? Because every non-clustered index carries a copy of it, and an increasing key means new rows go at the end with no page splits.

    Key Lookups: Running Back to the Shelf

    Analogy. The textbook index tells you "photosynthesis: page 45". But if you need the diagram caption too, you must flip to page 45. Doing that once is fine. Doing it for 50,000 index entries means flipping 50,000 times — at that point reading the whole book would have been faster.

    When a non-clustered index finds rows but doesn't contain all the columns the query needs, the engine performs a key lookup / bookmark lookup (SQL Server) or heap fetch (PostgreSQL) per row. For a few rows it's cheap; for many rows the optimiser often abandons the index and scans the table instead. This is a big reason "my index isn't being used".

    Covering Indexes: The Index Card That Already Has the Answer

    Analogy. Instead of an index entry saying "photosynthesis: page 45", imagine one that says "photosynthesis: page 45 — definition: process by which plants make food from light". If the definition is all you needed, you never open the book.

    A covering index contains every column the query needs, so no lookup is required:

    -- Query: SELECT order_ts, total_amount FROM orders WHERE customer_id = 42;
CREATE INDEX ix_orders_cust_cover
    ON orders (customer_id)              -- searched column (key)
    INCLUDE (order_ts, total_amount);    -- carried along at the leaf, not sorted on

    INCLUDE columns are stored only at the leaf level: they make the index cover the query without making the key wider.

    5.4 Composite Indexes and Column Order: The Phone Book

    Analogy. A phone book is sorted by last name, then first name. Finding "Sharma, Priya" is instant. Finding all "Sharmas" is instant. But finding everyone named "Priya" regardless of surname? You must read the whole book — the first-name sort is only useful within a surname.

    An index on (customer_id, order_ts):

    Query filter Can it seek efficiently?
    WHERE customer_id = 42 Yes (uses the leading column)
    WHERE customer_id = 42 AND order_ts >= '2024-01-01' Yes (perfect)
    WHERE customer_id = 42 ORDER BY order_ts Yes, and avoids a sort
    WHERE order_ts >= '2024-01-01' No seek (leading column missing) — at best a scan of the index

    This is the leftmost-prefix rule. Design rule of thumb: equality columns first, then range columns, then ORDER BY columns. Among equality columns, put the one used by the most queries first.

    5.5 Sargability: Don't Disguise the Column

    Analogy. You ask a librarian, "Find books whose title, when written backwards, starts with 'G'." Even though the catalogue is sorted by title, she can't use it — she'd have to reverse every title first. If you instead ask "find titles that end in 'g'", same problem. But "titles starting with 'Ga'" — instant.

    A predicate is SARGable (Search ARGument-able) when the engine can use an index to seek. Wrapping the indexed column in a function, arithmetic, or a type conversion hides it from the index.

    Non-sargable (forces scan) Sargable rewrite
    WHERE YEAR(order_ts) = 2024 WHERE order_ts >= '2024-01-01' AND order_ts < '2025-01-01'
    WHERE CAST(order_ts AS DATE) = '2024-10-13' WHERE order_ts >= '2024-10-13' AND order_ts < '2024-10-14'
    WHERE UPPER(email) = 'A@B.COM' Store normalised emails, or a functional index on UPPER(email)
    WHERE amount * 1.18 > 1000 WHERE amount > 1000 / 1.18
    WHERE name LIKE '%sharma' Leading wildcard can't seek; use full-text or trigram (pg_trgm) index
    WHERE phone = 9876543210 on a VARCHAR column WHERE phone = '9876543210' (avoid implicit conversion)
    WHERE ISNULL(status,'X') = 'OPEN' WHERE status = 'OPEN'
    WHERE col_a = 1 OR col_b = 2 May need two indexes, or rewrite as UNION ALL of two seeks

    Using half-open date ranges (>= start AND < next_start) is a habit worth building: it's sargable and also handles timestamps with time parts correctly, unlike BETWEEN '2024-10-13' AND '2024-10-13 23:59:59' which misses fractional seconds.

    5.7 The Price of Indexes: Every New Book Means Updating Every Catalogue

    Analogy. A library with five catalogues (by title, author, subject, ISBN, year) must update all five whenever a book arrives or moves. More catalogues = faster finding, slower shelving.

    Each index slows INSERT/UPDATE/DELETE, uses disk and memory, and needs maintenance. On write-heavy tables, a dozen indexes can make inserts crawl.

    • Find unused indexes: pg_stat_user_indexes (idx_scan = 0) in PostgreSQL; sys.dm_db_index_usage_stats in SQL Server (high user_updates, zero seeks/scans).
    • Find duplicate/overlapping indexes: an index on (a) is redundant if (a, b) exists.
    • Bulk loads: for large loads into indexed tables, it's often faster to disable/drop non-clustered indexes, load, then rebuild.
    • Missing-index suggestions (SQL Server DMVs, plan warnings) are hints, not orders. They ignore the write cost and often suggest overlapping indexes.

    5.8 Statistics: The Map the GPS Uses

    Analogy. Your GPS chooses a route based on its traffic data. If that data is from last year, it confidently routes you through a road that's now closed for construction. The GPS isn't "stupid" — it's working from a stale map.

    The query optimiser chooses a plan based on statistics: histograms describing how values are distributed (how many rows have status = 'OPEN', how many customers per region). From these it estimates row counts, then picks join order, join algorithms and memory grants.

    If statistics are stale (e.g., you just loaded 50 million rows into a table that had 1,000), estimates are wildly wrong: the engine might choose a nested loop expecting 10 rows and get 10 million.

    Practice: - After large loads or deletes, update statistics: ANALYZE table_name; (PostgreSQL), UPDATE STATISTICS dbo.table_name; (SQL Server), ANALYZE in Redshift, CREATE/UPDATE STATISTICS in Synapse dedicated pools. - Auto-stats exist but trigger on thresholds that large tables may not hit for a long time. - Skewed data (one customer with 40% of orders) fools averages; extended/multi-column statistics can help.

    5.9 Execution Plans: The GPS Route

    Analogy. Before driving, the GPS shows the planned route: "take highway, exit 14, turn left". An execution plan is the database's planned route for your query. EXPLAIN shows the plan it intends; EXPLAIN ANALYZE (or "actual execution plan") shows the route it actually took, with real timings and row counts.

    -- PostgreSQL
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;

-- SQL Server
SET STATISTICS IO, TIME ON;   -- then run query with "Include Actual Execution Plan"

-- MySQL 8
EXPLAIN ANALYZE SELECT ... ;

    What to look for, in order:

    1. Estimated vs actual rows. A mismatch of 10x or more is the root of most bad plans (stale stats, skew, non-sargable predicates, functions, table variables).
    2. The most expensive operator. Plans read right-to-left / inside-out (SQL Server) or bottom-up (PostgreSQL).
    3. Scans on large tables when you expected seeks.
    4. Key lookups executed thousands of times → consider a covering index.
    5. Sorts and hashes spilling to disk ("Sort Method: external merge" in PostgreSQL, spill warnings in SQL Server, "bytes spilled" in Snowflake) → insufficient memory, usually due to bad estimates.
    6. Implicit conversion warnings.
    7. Buffers/logical reads. Lower is better; this is the "pages touched" from Section 2.1.

    5.10 Join Algorithms: Three Ways to Match Guests to Tables

    Analogy. You must match 500 wedding guests to their reserved seats.

    • Nested loop: for each guest, walk through the seating chart to find their name. Great if there are only a few guests and the chart is alphabetised (indexed). Terrible for 500 guests and an unsorted chart.
    • Hash join: first, build a set of pigeonholes labelled by surname initial and drop each seat card into its pigeonhole (build phase). Then for each guest, go straight to their pigeonhole (probe phase). Excellent for large, unsorted inputs, as long as the pigeonholes fit in the room (memory).
    • Merge join: if both the guest list and the seating chart are already sorted alphabetically, walk down both lists together like closing a zip. Very efficient, but only if the inputs are sorted (or cheap to sort).
    Algorithm Best when Weakness
    Nested Loop Outer input small, inner side indexed on join key Explodes when outer input is large
    Hash Join Large unsorted inputs, equality joins Needs memory; spills to disk if underestimated; equality only
    Merge Join Both inputs already sorted on join key Sorting cost if not already sorted

    Seeing a nested loop over millions of rows usually means the optimiser thought the outer side was tiny → check statistics.

    5.11 Parameter Sniffing: A Tailor Who Remembers Only the First Customer

    Analogy. A tailor measures the first customer of the day, a child, and then sews every subsequent suit in that child's size because "that's the pattern for this order type". The next customer, a tall adult, gets a suit that doesn't fit.

    In SQL Server (and to a degree other engines with plan caching), a stored procedure's plan is compiled using the first parameter values it receives and then cached. If the first call is for a tiny customer (10 rows), the cached plan uses nested loops; when a huge customer (10 million rows) calls it, the same plan is disastrous.

    Remedies: OPTION (RECOMPILE) for queries where parameters vary wildly; OPTIMIZE FOR (@p UNKNOWN); Query Store plan forcing; splitting procedures by workload size; in SQL Server 2022, Parameter Sensitive Plan optimisation.

    5.12 A Repeatable Performance Tuning Workflow

    Analogy: a doctor doesn't prescribe before diagnosing. Symptoms → tests → diagnosis → treatment → follow-up.

    1. Identify the slow query from evidence: pg_stat_statements, SQL Server Query Store, slow query logs, warehouse query history. Rank by total time (duration × executions), not just the single slowest run — a 50 ms query run a million times a day matters more than a 30 s monthly report.
    2. Baseline: record duration, CPU, logical reads, rows returned.
    3. Read the actual plan (Section 5.9).
    4. Check the query text: SELECT *, non-sargable predicates, fan-out joins, DISTINCT hiding duplicates, correlated subqueries, scalar functions per row, OR across columns, implicit conversions.
    5. Check statistics freshness.
    6. Consider indexes: composite order, covering, filtered.
    7. Consider structure: partitioning, pre-aggregation, materialised views, summary tables.
    8. Re-measure and confirm improvement under realistic data volume.
    9. Document what you changed and why.

    5.13 Common Anti-Patterns

    • SELECT * — reads unneeded columns, defeats covering indexes, breaks when schemas change; in columnar warehouses it directly multiplies cost.
    • Row-by-row processing (RBAR — "Row By Agonising Row") with cursors or loops.

      Analogy: carrying groceries from the car one item at a time versus using a trolley. SQL is designed for the trolley (set-based operations).

    • Huge IN (...) lists — load the values into a temp table and join.
    • Deep OFFSET pagination — OFFSET 1000000 reads and discards a million rows.

      Analogy: to read page 500 of a book, you flick through 499 pages each time. A bookmark (keyset pagination) takes you straight there.

    sql -- Keyset pagination SELECT * FROM orders WHERE order_id > :last_seen_id ORDER BY order_id LIMIT 100; - COUNT(*) > 0 to test existence — use EXISTS, which stops at the first match. - Giant single-transaction updates — millions of rows in one statement cause log growth, lock escalation and painfully long rollbacks if it fails. Batch:

    sql -- SQL Server batching pattern WHILE 1 = 1 BEGIN UPDATE TOP (10000) dbo.orders SET status = 'ARCHIVED' WHERE status = 'CLOSED' AND order_ts < '2020-01-01'; IF @@ROWCOUNT = 0 BREAK; END - Functions on indexed columns in WHERE/JOIN (Section 5.5). - ORDER BY in views or subqueries that don't need it.

    Part 6: Scaling: partitioning, replication, sharding, CDC

    6.1 Partitioning: The Filing Cabinet with a Drawer per Year

    Analogy. An accountant keeps receipts in a filing cabinet with one drawer per month. To find March 2024 receipts, she opens only that drawer (partition pruning). At year-end, to discard receipts older than seven years, she pulls out the old drawer and shreds it in one go (partition drop), instead of hunting through every drawer pulling out individual receipts (DELETE WHERE date < …).

    Partitioning splits one logical table into physical pieces by a partition key. Queries see one table; the engine stores and manages pieces separately.

    Strategy How rows are assigned Typical use
    Range By value ranges (dates) Fact tables, events, logs — the most common
    List By explicit values Region, country, tenant
    Hash By hash of a key into N buckets Spreading load evenly when no natural range exists
    Composite Range then hash/list Very large multi-tenant event tables 
    -- PostgreSQL declarative partitioning
CREATE TABLE fact_events (
    event_id   BIGINT,
    event_ts   TIMESTAMPTZ NOT NULL,
    user_id    BIGINT,
    payload    JSONB
) PARTITION BY RANGE (event_ts);

CREATE TABLE fact_events_2024_10 PARTITION OF fact_events
    FOR VALUES FROM ('2024-10-01') TO ('2024-11-01');

    Benefits: 1. Pruning — queries filtered on the partition key read only relevant partitions. 2. Lifecycle management — drop or archive old partitions instantly. 3. Partition switching / exchange — load a staging table, validate it, then swap it into the main table as a metadata-only operation.

    Analogy: instead of unloading a delivery truck box by box onto shelves while customers wait, you prepare a full drawer in the back room and slide the whole drawer into the cabinet in one second. This makes reloads atomic and idempotent (re-running replaces the drawer rather than adding duplicates). 4. Maintenance per partition — rebuild indexes or update stats on just the active partition.

    Pitfalls: - Queries that don't filter on the partition key scan every partition (often slower than an unpartitioned table). - Too many small partitions (e.g., hourly for years) add planning overhead. - Unique constraints/primary keys usually must include the partition key. - Choose a key that matches how data is queried and loaded — usually the event/business date, not the load date (unless loads are always by load date).

    6.2 Replication: Photocopies of the Master Ledger

    Analogy. A bank branch has one master ledger where all entries are written. To let many auditors read without crowding the clerk, the branch keeps photocopies in other rooms that are updated as new entries are made. Auditors read the copies; only the clerk writes in the master.

    • Primary (writer) → replicas (readers). Writes go to the primary; the log is shipped to replicas and replayed.
    • Synchronous replication — registered post with signed receipt: the primary waits until the replica confirms before acknowledging commit. No data loss on failover, but each write is slower.
    • Asynchronous replication — ordinary post: the primary doesn't wait. Fast, but the replica may lag, and recent transactions can be lost if the primary dies.
    • Physical replication copies storage-level changes (whole database). Logical replication copies row-level changes for chosen tables, and can feed other systems.

    For a data engineer: - Run heavy extracts against a read replica, not the production primary. - Check replication lag before extracting. If the replica is 2 hours behind, your "up to midnight" extract is missing data. Record the replica's replay position/timestamp with each extract. - Long-running queries on a replica can conflict with log replay (PostgreSQL "canceling statement due to conflict with recovery"); tune max_standby_streaming_delay / hot_standby_feedback or use smaller batches.

    6.3 Sharding: Bank Branches by Region

    Analogy. A national bank doesn't keep every customer's account in one building. Customers in the north are served by the northern branch, southern customers by the southern branch. Each branch is independent and handles its own load. But "total deposits across the country" now requires calling every branch, and transferring between branches is complicated.

    Sharding splits data across multiple independent database servers by a shard key (customer_id, tenant_id, region). It provides horizontal write scaling but complicates cross-shard queries, transactions, joins, and rebalancing when one shard gets too big.

    As a data engineer you'll mostly consume from sharded systems: extracting from N databases with identical schemas and unioning results, adding a shard_id/source_db column so keys stay unique.

    6.4 Change Data Capture: CCTV for Your Tables

    Analogy. To know what changed in a shop overnight, you could recount every item every morning (full extract), or check the "last modified" sticker on each item (timestamp incremental), or simply watch the CCTV footage which shows every item being added, moved or removed, in order (CDC). CCTV even shows items that were taken away — something stickers can never tell you.

    CDC reads the database's transaction log (Section 2.3) and emits every INSERT, UPDATE and DELETE as an event, in commit order, typically with before/after values.

    Tools: Debezium (Kafka-based, open source), SQL Server CDC / Change Tracking, Oracle GoldenGate / LogMiner, AWS DMS, Azure Data Factory CDC, Fivetran, Qlik Replicate, Snowflake Streams (CDC within Snowflake), Delta Change Data Feed.

    Advantages: captures hard deletes; minimal load on the source (no repeated big queries); near-real-time; exact ordering.

    Challenges: setup requires DBA privileges and log retention configuration; schema changes must be handled; you must apply the change stream correctly (dedupe, order by log sequence number, handle updates to the same key multiple times in a batch); initial snapshot plus streaming must be stitched without gaps or duplicates.

    Part 7: DBA responsibilities

    The overall analogy. If the database is a building, the DBA is the facilities manager: controls who has keys (security), has insurance and spare keys stored off-site (backups), keeps a generator ready (high availability), cleans and repairs regularly (maintenance), watches the CCTV and fire alarms (monitoring), plans for more tenants (capacity), and approves renovations so nobody knocks down a load-bearing wall (change management).

    Even with dedicated DBAs or a managed cloud service, a 3-year data engineer is expected to understand all of this, and often to do much of it for the warehouse and pipeline databases.

    7.1 Security

    Authentication vs Authorisation: The Office Building

    Analogy. At an office building, reception checks your ID (authentication: who are you?). Then your keycard opens only certain floors (authorisation: what are you allowed to do?).

    Authentication best practices: - Use central identity: Azure AD / Entra ID, AWS IAM, Okta, SSO, rather than local database passwords. - Pipelines use service principals / managed identities / service accounts, never a person's login. When that person leaves, nothing breaks, and audit logs show "pipeline X did this", not "Ravi did this at 3 am". - Enforce MFA for human access; rotate credentials; disable shared generic logins like sa / admin.

    Role-Based Access Control (RBAC): Hotel Keycards

    Analogy. A hotel doesn't program each guest's card individually for each door. It defines roles: "guest on floor 5" opens room 512 and the gym; "housekeeping" opens every guest room on their floor; "manager" opens everything. Staff are assigned roles, and roles hold the permissions.

    Grant privileges to roles, then assign users/groups to roles. Never grant directly to individuals.

    -- Read-only analyst role on the marts
CREATE ROLE analyst_ro;
GRANT USAGE ON SCHEMA mart TO analyst_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA mart TO analyst_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA mart GRANT SELECT ON TABLES TO analyst_ro;  -- future tables too

-- Pipeline role writes only to its own schemas
CREATE ROLE etl_sales_rw;
GRANT USAGE, CREATE ON SCHEMA staging_sales TO etl_sales_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA mart_sales TO etl_sales_rw;

GRANT analyst_ro TO "jane.doe@company.com";

    Least privilege: the hotel guest's card opens their room, not the whole hotel. Give the minimum required. A compromised read-only reporting account should not be able to drop tables.

    Typical role layers: raw_reader, staging_writer, mart_reader, mart_writer, pii_reader, admin. Separate roles for dev, test and prod; production write access for humans should be rare and audited.

    Row-Level Security (RLS): Each Teacher Sees Only Their Class

    Analogy. All student records sit in one school database, but when Ms. Iyer opens the gradebook, she sees only her class. Same table, filtered by who is looking.

    -- PostgreSQL
ALTER TABLE fact_sales ENABLE ROW LEVEL SECURITY;
CREATE POLICY region_policy ON fact_sales
    USING (region = current_setting('app.user_region'));

    SQL Server uses security predicates with CREATE SECURITY POLICY; Snowflake uses row access policies; BigQuery uses row-level access policies; Power BI has its own RLS layer.

    Column Security and Dynamic Data Masking: The Credit Card Receipt

    Analogy. A shop receipt prints your card as XXXX-XXXX-XXXX-1234. The shop's system knows the full number, but the printout hides it from anyone who sees the receipt.

    • Column-level permissions: deny SELECT on sensitive columns to most roles.
    • Dynamic data masking: users without privilege see masked values (p****@gmail.com, XXXXXX1234), while privileged roles see the real value. Available in SQL Server/Azure SQL, Snowflake (masking policies), BigQuery (data masking via policy tags), Databricks (column masks).
    • Static masking / tokenisation / pseudonymisation: replace real values permanently in non-production copies. Never copy raw production PII into dev environments.

    Encryption: The Safe and the Armoured Truck

    Analogy. Money in the bank is kept in a safe (encryption at rest). When it moves between branches, it travels in an armoured truck (encryption in transit). Both are needed.

    • At rest: Transparent Data Encryption (TDE), cloud-managed or customer-managed keys (CMK) in Key Vault / KMS. Protects against someone stealing disks or backup files.
    • In transit: enforce TLS on all connections; reject unencrypted connections.
    • Column-level / application encryption: for extremely sensitive fields (SQL Server Always Encrypted), where even DBAs can't read the plaintext.

    Secrets Management: Don't Tape the Key Under the Doormat

    Credentials, connection strings and API keys belong in a secrets manager (Azure Key Vault, AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager), retrieved at runtime. Never hard-code them in scripts, notebooks, config files committed to Git, or .env files that get shared. Use secret-scanning in CI to catch leaks. If a secret is ever committed, rotate it immediately — deleting the commit is not enough.

    Auditing: The Visitor Logbook

    Record who logged in, who read sensitive tables, and who changed schemas or permissions (SQL Server Audit, PostgreSQL pgaudit, Snowflake ACCESS_HISTORY/QUERY_HISTORY, cloud audit logs). Review periodically, and retain logs according to policy.

    7.2 Backup and Recovery

    RPO and RTO: How Much Can You Lose, and How Long Can You Be Down?

    Analogy. You're writing a long essay. - RPO (Recovery Point Objective) — "If my laptop dies, how much writing can I afford to lose?" If you save every 10 minutes, your RPO is 10 minutes. - RTO (Recovery Time Objective) — "How quickly must I be writing again after the crash?" If you need to borrow a laptop, download the file, and reopen it within 30 minutes, your RTO is 30 minutes.

    These are business decisions, agreed with stakeholders, and they drive every technical choice. A payments database might need RPO ≈ 0 and RTO of minutes; a monthly reporting mart might accept RPO of 24 hours and RTO of a day (because it can be rebuilt from sources).

    Backup Types: The Photo Album and the Diary

    Analogy. To preserve the state of your house: - A full backup is a complete photo album of every room. - A differential backup is photos of everything that has changed since the last full album (each new differential grows until the next full). - A log / incremental backup is a diary of every single change, in order: "10:02 moved chair; 10:05 painted wall".

    To restore your house to exactly how it was at 10:04 last Tuesday, take the last full album, apply the latest differential, then replay the diary up to 10:04. That's point-in-time recovery (PITR).

    Type Contains Restore needs Trade-off
    Full Everything Just this backup Biggest and slowest to take
    Differential Changes since last full Full + latest differential Grows over the week
    Incremental / Log Changes since last backup of any kind Full + (diff) + every log in sequence Small, frequent; long chain to replay

    A typical schedule: weekly full, daily differential, transaction log backups every 5–15 minutes (giving an RPO of 5–15 minutes).

    Platform specifics: - SQL Server: recovery models matter. FULL recovery allows log backups and PITR; SIMPLE does not (the log is truncated automatically, so you can only restore to the last full/diff). Choosing SIMPLE on a database that needs PITR is a classic mistake; choosing FULL and never taking log backups causes the log to grow forever. - PostgreSQL: pg_basebackup (physical full) + continuous WAL archiving gives PITR; tools like pgBackRest or Barman manage this. pg_dump is a logical backup (SQL/scripts) — portable and good for single databases or migrations, but slower to restore and no PITR. - Managed cloud databases (Azure SQL, Amazon RDS/Aurora, Cloud SQL) automate backups and PITR within a retention window (often 7–35 days). You must still know the retention, the restore procedure, and how long it takes. - Warehouses: Snowflake Time Travel (query or restore data as of a past time, 1–90 days) and Fail-safe (7 extra days, recoverable via support), UNDROP TABLE, zero-copy clones; BigQuery time travel (up to 7 days) and table snapshots; Delta Lake / Iceberg table versions (RESTORE TABLE … TO VERSION AS OF, limited by VACUUM retention).

    The Golden Rule: Test Your Restores

    Analogy. A fire extinguisher that has never been checked might be empty. You find out during the fire. A fire drill reveals the blocked exit before it matters.

    A backup that has never been test-restored is a hope, not a backup. Schedule regular restore drills: restore to a separate server, run integrity checks and row-count comparisons, and measure the time against your RTO. Also verify backups are stored off-site / in another region and protected from deletion (immutable or locked storage), so ransomware or an accidental script can't destroy both the database and its backups.

    Logical Recovery vs Disaster Recovery

    Most real-world "recoveries" aren't disasters; they're someone ran DELETE without a WHERE or a pipeline loaded bad data. For these, the fastest tools are: Time Travel/table versions, restoring a single table from a PITR copy into a side database and copying rows back, or re-running idempotent pipelines for the affected dates. Know these paths before you need them.

    7.3 High Availability (HA) and Disaster Recovery (DR)

    Analogy. - HA is the spare tyre in your car: a puncture (a server failure) and you're back on the road in minutes, same trip. - DR is a second house in another city: if your city floods (a whole data centre or region fails), you move there. It's slower and costlier, but you still have a home.

    HA (within a region): - Automatic failover to a synchronous standby: SQL Server Always On Availability Groups / Failover Cluster Instances, PostgreSQL with Patroni / repmgr, MySQL Group Replication, cloud multi-AZ deployments. - Applications connect via a listener / virtual endpoint so failover is transparent apart from a brief disconnect. Pipelines must retry on connection failures.

    DR (across regions): - Asynchronous geo-replication (Azure SQL geo-replication / failover groups, Aurora Global Database, cross-region read replicas, Snowflake database replication and failover groups), or geo-redundant backups. - A written runbook: who declares a disaster, the exact failover steps, DNS/connection string changes, how pipelines are repointed, and how to fail back. - Rehearse it. An untested DR plan typically fails at the step nobody remembered (firewall rules, secrets in the other region, scheduled jobs that weren't replicated).

    7.4 Routine Maintenance

    Statistics Updates — Updating the Census

    Analogy: a government plans schools and hospitals from census data. If the census is 20 years old, it builds schools in the wrong places.

    Covered in Section 5.8. Schedule statistics updates after large loads, and a regular sweep (e.g., nightly or weekly) for the rest.

    Index Fragmentation — A Binder with Shuffled Pages

    Analogy: a binder starts with pages in order. Over time, you insert new pages in the middle; full sections split, and pages end up out of order and half-empty. Reading it front to back means constantly jumping around, and the binder is fatter than it needs to be.

    Inserts and updates cause page splits, leading to logical fragmentation (out-of-order pages) and low page density (half-empty pages).

    • SQL Server: check sys.dm_db_index_physical_stats. A commonly used guideline is reorganise at moderate fragmentation (roughly 5–30%) and rebuild above that. On modern SSD/SAN storage, fragmentation matters much less than it used to; page density and up-to-date statistics matter more. Rebuilds also refresh statistics. Use ONLINE = ON (Enterprise/Azure) to avoid blocking. Ola Hallengren's maintenance solution is the industry-standard script set.
    • PostgreSQL: REINDEX CONCURRENTLY for bloated indexes; pg_repack to rebuild bloated tables online.
    • Fill factor: leaving free space in pages (e.g., 90%) reduces page splits for tables with random inserts/updates, at the cost of more pages.

    VACUUM (PostgreSQL) — Clearing Tables in a Restaurant

    Analogy: after diners leave, their dirty plates stay on the table until a waiter clears it. If nobody clears tables, the restaurant fills up with empty-but-occupied tables and new customers can't sit down.

    Because of MVCC (Section 2.7), updates and deletes leave dead tuples. VACUUM marks their space reusable; autovacuum does this automatically in the background; VACUUM FULL rewrites the table to shrink it (but takes an exclusive lock — avoid on busy tables, use pg_repack). ANALYZE (often run together) refreshes statistics.

    Transaction ID wraparound — the odometer rollover.

    Analogy: an old car's odometer rolls over from 999,999 back to 000,000. Suddenly the car "looks" brand new and its service history makes no sense.

    PostgreSQL transaction IDs are 32-bit. Without vacuum "freezing" old rows, IDs approach wraparound, and PostgreSQL will eventually refuse writes to protect data. Monitor age(datfrozenxid), ensure autovacuum keeps up on large tables, and watch for long-running or idle-in-transaction sessions, which block cleanup.

    Redshift: VACUUM re-sorts and reclaims space (largely automatic now) and ANALYZE refreshes statistics. Delta Lake: OPTIMIZE compacts files and VACUUM deletes old unreferenced files (which also limits time travel).

    Integrity Checks — The Annual Health Check-Up

    SQL Server DBCC CHECKDB detects physical and logical corruption. Run it regularly (on a restored copy if the production database is large), and treat any error as urgent. PostgreSQL has amcheck for index verification and page checksums for corruption detection.

    Log and Disk Management — The Overflowing Bin

    Transaction logs grow when log backups don't run (SQL Server FULL recovery), when a long transaction is open, or when replication/CDC readers fall behind and the log can't be truncated. Monitor log size and free disk space; a full disk is one of the most common, and most avoidable, outages. Also watch tempdb (SQL Server), which fills from large sorts, spills, version store and temp tables.

    Data Retention and Archiving — Clearing the Attic

    Agree retention per dataset (legal, regulatory, business need). Implement it with partition drops or archiving to cheaper storage (data lake, cold storage tiers), not with giant DELETE statements. Retention is also a privacy requirement, not just housekeeping.

    7.5 Monitoring: The Car Dashboard

    Analogy. A car dashboard shows speed, fuel, engine temperature and warning lights. You don't stare at it constantly, but a warning light demands attention before the engine seizes.

    Category What to watch Why
    Resources CPU, memory, disk I/O latency, free disk, log size, tempdb Saturation causes everything to slow
    Workload Top queries by total time, queries/sec, long-running queries Find what to tune
    Contention Blocking chains, lock waits, deadlocks Users stuck waiting
    Wait statistics What the engine spends time waiting on Diagnosis (see below)
    Health Backup success/age, replication lag, failed logins, connection count vs max Silent failures become disasters
    Warehouse Credit/slot consumption, queue time, spill to disk, bytes scanned Performance = cost in the cloud
    Pipelines Job duration trend, row counts, freshness Early signs of data issues

    Wait statistics — the hospital visit breakdown.

    Analogy: you spent 4 hours at a hospital. Was it waiting for registration, for the doctor, for X-ray, or for the pharmacy? Knowing where you waited tells you what to fix.

    SQL Server's sys.dm_os_wait_stats (and Azure SQL equivalents) and PostgreSQL's pg_stat_activity.wait_event show what sessions wait on: disk I/O (PAGEIOLATCH_*), locks (LCK_M_*), CPU (SOS_SCHEDULER_YIELD), parallelism (CXPACKET/CXCONSUMER), memory grants (RESOURCE_SEMAPHORE), log writes (WRITELOG). The top waits point you straight to the bottleneck.

    Useful tools: pg_stat_statements, pg_stat_activity, pg_locks; SQL Server Query Store, DMVs, Extended Events, sp_WhoIsActive; cloud monitoring (Azure Monitor, CloudWatch, Cloud Monitoring); Datadog, Grafana/Prometheus; warehouse account usage views.

    Alert design: alert on things that need human action (backup failed, disk 85% full, replication lag > 15 min, pipeline missed SLA). Too many noisy alerts train people to ignore all of them — the "boy who cried wolf" problem.

    7.6 Capacity Planning: Planning for More Tenants

    Analogy. A building manager notices two new families move in each month. With 20 flats free, she knows the building is full in 10 months and starts planning an extension now, not when the last flat is taken.

    Track growth trends (rows/day, GB/month, peak concurrent users, peak CPU), project 6–12 months forward, and act before limits: storage, partitions to create, compute tier, connection limits, and ID column overflow (Section 3.2). In the cloud, capacity planning is mostly cost forecasting: growth × unit price.

    7.7 Schema Change Management: Renovating Without Collapsing the Building

    Analogy. You don't let random tenants knock down walls. Renovations need approved plans, are done by qualified contractors, and are recorded in the building's documents so the next manager knows what's behind each wall.

    Principles: - No manual changes in production. All DDL lives in version control (Git). - Use migration tools: Flyway, Liquibase, sqitch, Alembic (Python), SSDT / DACPAC (SQL Server), dbt for warehouse models and Terraform for warehouse objects/permissions. - Changes go through pull requests and code review, then CI/CD promotes them dev → test → prod. - Every migration should be repeatable and ideally reversible (or have a documented roll-forward fix).

    Zero-Downtime Changes: Expand–Contract (Build the New Bridge First)

    Analogy. To replace an old bridge, you build the new bridge beside it, divert traffic onto the new one, and only then demolish the old one. Traffic never stops.

    Example: renaming customer.phone to customer.mobile_number.

    1. Expand: add mobile_number (nullable). Nothing breaks.
    2. Dual write: update the application/pipelines to write to both columns.
    3. Backfill: copy existing phone values into mobile_number in batches.
    4. Switch reads: move every reader (reports, pipelines, views) to mobile_number.
    5. Contract: after confirming nothing reads phone (check query logs, lineage), drop it.

    Dangerous operations to handle with care: changing a column's data type on a big table (may rewrite the whole table and lock it); adding NOT NULL to a large table (full scan for validation); creating indexes without CONCURRENTLY (PostgreSQL) or ONLINE = ON (SQL Server); adding foreign keys on big tables (validate separately with NOT VALID then VALIDATE CONSTRAINT in PostgreSQL); dropping columns that downstream views or BI reports still use.

    Downstream impact: before changing a table, check lineage (Section 11.3) for every pipeline, view, dashboard and extract that depends on it, and notify consumers.

    Part 8: Data warehouse design

    8.1 Architectural Approaches: Different Ways to Build a Shopping Mall

    Kimball (dimensional, bottom-up).

    Analogy: build the mall one shop at a time — first the grocery store (sales mart), then the pharmacy (inventory mart) — but insist from day one that all shops share the same car park, the same entrances and the same signage (conformed dimensions). Customers get value quickly, and the shops still feel like one mall.

    Business-process star schemas linked by conformed dimensions through a bus architecture. Fast to deliver; the most widely used approach.

    Inmon (Corporate Information Factory, top-down).

    Analogy: first build a giant central distribution warehouse where every product from every supplier is stored in a standard, highly organised way (normalised 3NF enterprise data warehouse). Then ship goods out to individual shops (dimensional data marts) designed for their customers.

    Strong integration and a single version of truth, but a long time before users see anything.

    Data Vault 2.0.

    Analogy: LEGO. Hubs are the base bricks, each representing a core business concept by its business key (Customer, Product). Links are the connector pieces joining hubs (Customer-bought-Product). Satellites are the decorative stickers attached to bricks, each stamped with the date it was stuck on (descriptive attributes with full history). You can keep adding new bricks and stickers as new sources arrive, without rebuilding the model.

    Highly auditable, insert-only, resilient to source changes, parallel-loadable; suits many-source, regulated environments. Not query-friendly on its own, so you add a dimensional layer ("information marts") on top.

    Lakehouse and the Medallion Architecture.

    Analogy: a water treatment plant. - Bronze: raw river water collected exactly as it arrives — muddy, but you keep it so you can always re-treat it differently. - Silver: filtered and purified — trusted, consistent, safe to use. - Gold: bottled, labelled and packed for specific customers — business-ready.

    The data lives in open file formats (Parquet, with table formats like Delta Lake, Apache Iceberg, Apache Hudi) on object storage, with warehouse features: ACID transactions, schema enforcement, time travel. Platforms: Databricks, Microsoft Fabric, Snowflake with Iceberg tables, BigQuery with BigLake.

    In practice: most modern platforms combine these — medallion layers to organise flow, Kimball star schemas in the gold layer, sometimes Data Vault in silver for heavily regulated or many-source environments.

    8.2 Facts and Dimensions: The Shop Receipt

    Analogy. Look at a shop receipt. - The numbers — quantity 2, unit price ₹45, discount ₹10, total ₹80 — are facts (measures). You add them up, average them, compare them. - Everything that gives those numbers context — who bought (customer), what (product), where (store), when (date/time), how (payment method), why (promotion) — are dimensions.

    Analysts' questions sound like: "Sum of sales (fact) by region and month (dimensions)". Facts are the verbs and numbers; dimensions are the nouns and adjectives you slice by.

    8.3 The Four-Step Dimensional Design Process

    1. Choose the business process — a real operational activity that generates events: taking orders, shipping, claims processing, website sessions. (Not a department, and not a report.)
    2. Declare the grain — the precise meaning of one fact row.
    3. Identify the dimensions — the descriptive context true at that grain.
    4. Identify the facts — the numeric measurements true at that grain.

    Grain: The Zoom Level of a Map

    Analogy. A map at street level shows every house; at city level, only districts. You can always zoom out from street level (aggregate), but you can never zoom in from a city-level map to see a house that was never drawn.

    Grain is "what does exactly one row represent?" For example: "one row per product per order line", "one row per account per day", "one row per shipment".

    Rules: - Write the grain down in one sentence before designing anything else. - Prefer the lowest (atomic) grain available — it answers the widest range of questions; you can always aggregate up. - Never mix grains in one fact table (e.g., order-line rows and order-header shipping charges in the same table). Mixed grains cause double counting and confusion. Either allocate header-level amounts down to lines, or create a separate fact table.

    8.4 Types of Fact Tables

    Transaction fact — the receipt roll.

    Every sale prints a new receipt line. Nothing is ever updated.

    One row per event at the moment it happened. The most common type. Example: fact_sales at order-line grain.

    Periodic snapshot fact — the monthly bank statement.

    Each month the bank tells you your balance at month-end, whether or not you made any transactions.

    One row per entity per period, regardless of activity. Examples: daily inventory on hand per product per store; monthly account balance; daily active subscription count. Great for measuring levels rather than flows.

    Accumulating snapshot fact — the parcel tracking page.

    A courier's tracking page shows one shipment with several milestone dates: ordered 3 Oct, packed 4 Oct, shipped 5 Oct, out for delivery 7 Oct, delivered 7 Oct. The same record is updated as each milestone happens.

    One row per process instance, with multiple date keys for milestones and lag measures between them (days_order_to_ship). Examples: order fulfilment pipelines, loan applications, insurance claims, recruitment funnels. Unlike other facts, these rows are updated.

    Factless fact — the attendance register.

    A class register records that a student attended on a day. There's no number to add up — the event itself is the fact.

    Records that something happened (or could happen) with no numeric measure. You COUNT(*) it. Examples: student attendance; which products were on promotion in which stores on which days (a "coverage" table — combined with sales, it answers "which promoted products did not sell?").

    Measure Additivity: What Can You Safely Add Up?

    Analogy. - Fully additive — cash in wallets. Total cash across all people, all days, all cities: just add. - Semi-additive — bank balances. Add balances across accounts on a given day (total deposits held today): fine. Add your own balance across 30 days: meaningless — you don't have 30× your money. For time, use the latest or average balance. - Non-additive — exam percentages. You can't add 80% and 60% to get 140%. You must sum marks obtained and marks possible separately, then divide.

    Type Example How to aggregate
    Additive sales amount, quantity, cost SUM across all dimensions
    Semi-additive account balance, inventory level, headcount SUM across non-time dimensions; LAST/AVG over time
    Non-additive margin %, unit price, ratios, distinct counts Store components (numerator, denominator); compute at query time

    Design rule: store additive components in the fact table (gross_amount, cost_amount) and compute ratios (margin_pct) in the semantic/BI layer.

    8.5 Dimension Tables in Depth

    Dimensions are wide (dozens or hundreds of descriptive columns), denormalised (product row includes category and department names directly), and keyed by a surrogate key. Richer dimensions = more ways to slice data. Use readable descriptive values ("Credit Card", not "CC"; "Yes"/"No" rather than 1/0) because these become filter labels in dashboards.

    Surrogate Keys in Dimensions — Why Not Just Use the Source ID?

    Analogy. Two schools merge. Both had a student with roll number 101. The merged school issues new admission numbers, while keeping the old roll numbers as reference attributes.

    Reasons for warehouse surrogate keys: (1) integrate multiple sources whose IDs collide; (2) support SCD Type 2 history, where one customer has several versions and each needs its own key; (3) handle unknown/missing members (-1); (4) insulate the warehouse from source key changes or reuse; (5) compact integer joins are fast.

    The Date Dimension — The Wall Calendar with Notes

    Analogy: a printed planner where every day already shows the weekday, week number, month name, quarter, fiscal period, whether it's a public holiday, and whether it's a weekend.

    Pre-generate one row per date for many years (e.g., 2000–2040). Typical columns: date_key (smart integer like 20241014 — readable and naturally ordered), full_date, day_name, day_of_week, is_weekend, week_of_year, iso_week, month_num, month_name, quarter, year, fiscal_week, fiscal_month, fiscal_quarter, fiscal_year, is_public_holiday (per country if needed), is_last_day_of_month, same_day_last_year. Analysts should never compute fiscal periods with ad-hoc formulas. If you need time of day, create a separate time dimension (one row per minute or second) rather than one row per timestamp.

    Conformed Dimensions and the Bus Matrix — The Common Currency

    Analogy. Several countries agree to use the same currency. Now prices in any of them can be compared and combined directly. If each used its own currency with no exchange rate, comparisons would be meaningless.

    A conformed dimension has the same keys, attributes and meaning wherever it's used. If fact_sales and fact_returns both use the same dim_product and dim_date, you can compute return rates by product category and month with confidence (drill-across).

    The bus matrix is the planning grid:

    Business process Date Customer Product Store Promotion Supplier
    Sales ✔ ✔ ✔ ✔ ✔
    Returns ✔ ✔ ✔ ✔
    Inventory snapshot ✔ ✔ ✔
    Purchasing ✔ ✔ ✔

    Columns that recur across rows are your most important conformed dimensions; build them carefully once.

    Role-Playing Dimension — One Actor, Many Roles

    Analogy: one actor plays three characters in the same film, with different costumes.

    One physical dim_date plays "order date", "ship date" and "delivery date" in an accumulating snapshot. Implement with views (dim_order_date, dim_ship_date) or table aliases, so each role has clearly named columns in the BI tool.

    Degenerate Dimension — The Receipt Number

    Analogy: the receipt number identifies the receipt, but there's nothing else to say about it — no "receipt name" or "receipt category".

    A dimension key (order number, invoice number, transaction ID) stored directly in the fact table with no dimension table. Useful for grouping lines back into orders and for tracing to the source.

    Junk Dimension — The Kitchen Drawer

    Analogy: every kitchen has a drawer for small odds and ends — batteries, rubber bands, birthday candles. They don't deserve their own cupboard each, but you don't want them scattered on the counter.

    Combine several low-cardinality flags and indicators (is_gift_wrapped, payment_type, order_channel, is_express_delivery) into one small dimension containing their combinations. The fact gets one key instead of five flag columns.

    Mini-Dimension — Splitting Off the Fast-Changing Parts

    Analogy: instead of reprinting a customer's whole ID card every time their age band or loyalty tier changes, you give them a small separate sticker that is replaced frequently.

    For very large dimensions with a few rapidly changing attributes (age band, income band, credit score band), move those attributes into a small mini-dimension referenced directly by the fact. This prevents an SCD2 customer dimension exploding into millions of versions.

    Bridge Table — Shared Ownership

    Analogy: a house jointly owned by three siblings. If you attach the house's full value to each sibling and sum by sibling, you've tripled the value of the house.

    For many-to-many relationships between a fact and a dimension (a bank account with multiple holders, a patient encounter with multiple diagnoses, a sale credited to multiple salespeople), a bridge table sits between them, often with a weighting factor (e.g., 0.33 each) so allocations sum to 100% and totals aren't double counted.

    Outrigger and Hierarchies

    An outrigger is a secondary dimension referenced by a dimension (e.g., dim_customer → dim_date for first purchase date). Use sparingly. Hierarchies (department → category → subcategory → product) are usually flattened into columns of the dimension. Ragged/variable-depth hierarchies (org charts) use a bridge/closure table or path columns.

    Unknown and Special Members — The "Guest" Customer

    Analogy: a shop serves walk-in customers who don't give their details. The receipt still prints — under "Guest".

    Every dimension gets special rows such as -1 = 'Unknown', -2 = 'Not Applicable', -3 = 'Late Arriving / Pending'. When a fact's dimension value is missing or unmatched, it points to one of these instead of NULL. Facts never get silently dropped by inner joins, totals reconcile, and the unknown bucket is visible in reports so data quality issues are noticed.

    8.6 Slowly Changing Dimensions (SCD)

    The core question: when a dimension attribute changes, what should historical facts show? Priya lived in Mumbai until June, then moved to Bengaluru. Her March purchases — should a regional sales report show them under Mumbai (where she was then) or Bengaluru (where she is now)? The business must answer this per attribute. The SCD type is how you implement the answer.

    Type 0 — Retain original (the birth certificate).

    Your birth certificate never changes, even if you move.

    The value is fixed at first load and never updated. E.g., original_signup_channel, date_of_birth, first_order_date.

    Type 1 — Overwrite (updating a contact in your phone).

    When a friend changes number, you overwrite the old one. You no longer know the old number, and you don't care.

    Update in place; history is lost; all past facts now show the new value. Use for corrections (typos) and attributes where history doesn't matter.

    Type 2 — Add a new row (the address history on a passport application).

    A visa form asks for every address you've lived at, with from and to dates. Each address is a separate entry.

    When a tracked attribute changes, expire the current row (set its end date and is_current = false) and insert a new row with a new surrogate key. Facts loaded while Priya lived in Mumbai keep pointing to the Mumbai row's key; new facts point to the Bengaluru row. History is perfectly preserved. This is the most important SCD type to master.

    customer_sk customer_id name city effective_from effective_to is_current
    1001 C42 Priya Mumbai 2022-01-15 2024-06-30 false
    2378 C42 Priya Bengaluru 2024-07-01 9999-12-31 true

    Type 3 — Add a "previous value" column (the "formerly known as" note).

    A company's profile says "Name: Meta Platforms (formerly Facebook)".

    Keep current_region and previous_region columns. Supports exactly one level of history; used for planned changes like sales territory realignments where people want to compare "old vs new" structure.

    Type 4 — History table (the archive room). Keep the current row in the main dimension and full history in a separate history table. Useful for very large, frequently changing dimensions.

    Type 6 — Hybrid (1 + 2 + 3). Type 2 history rows, plus a current_city column on every row (overwritten Type 1 style). Reports can group by either "city at time of sale" (city) or "city today" (current_city) without complex joins.

    SCD Type 2 Implementation

    CREATE TABLE dim_customer (
    customer_sk      BIGINT IDENTITY PRIMARY KEY,   -- surrogate key
    customer_id      VARCHAR(50)  NOT NULL,         -- business key
    customer_name    VARCHAR(200),
    city             VARCHAR(100),
    segment          VARCHAR(50),
    row_hash         CHAR(64)     NOT NULL,         -- hash of SCD2-tracked columns
    effective_from   DATE         NOT NULL,
    effective_to     DATE         NOT NULL DEFAULT '9999-12-31',
    is_current       BOOLEAN      NOT NULL DEFAULT TRUE,
    created_batch_id BIGINT,
    updated_batch_id BIGINT
);

    Staging step: compute the hash of tracked columns, normalising NULLs and whitespace so they hash consistently:

    -- Example (Snowflake/Databricks style functions)
SELECT customer_id, customer_name, city, segment,
       SHA2(CONCAT_WS('|',
            COALESCE(TRIM(customer_name),''),
            COALESCE(TRIM(city),''),
            COALESCE(TRIM(segment),'')), 256) AS row_hash
FROM stg_customer_dedup;   -- already one row per customer_id

    Load step (one transaction):

    BEGIN;

-- 1. Expire current rows whose tracked attributes changed
UPDATE dim_customer d
SET    effective_to = CURRENT_DATE - 1,
       is_current   = FALSE,
       updated_batch_id = :batch_id
FROM   stg_customer s
WHERE  d.customer_id = s.customer_id
  AND  d.is_current  = TRUE
  AND  d.row_hash   <> s.row_hash;

-- 2. Insert new versions (changed) and new customers (never seen)
INSERT INTO dim_customer (customer_id, customer_name, city, segment, row_hash,
                          effective_from, created_batch_id)
SELECT s.customer_id, s.customer_name, s.city, s.segment, s.row_hash,
       CURRENT_DATE, :batch_id
FROM   stg_customer s
LEFT JOIN dim_customer d
       ON d.customer_id = s.customer_id AND d.is_current = TRUE
WHERE  d.customer_id IS NULL;   -- no current row: new customer, or expired in step 1

COMMIT;

    Why does step 2 catch both cases? After step 1, changed customers no longer have a current row, so they look "new" to the LEFT JOIN — exactly like brand-new customers.

    Refinements in real systems: use the source change timestamp (not CURRENT_DATE) as effective_from when available, so history is accurate even if loads are delayed; use timestamps rather than dates if changes can happen more than once a day; decide which columns are Type 1 (update in place on all versions) vs Type 2 (new row); and handle deleted source records (flag as is_deleted, expire the row). dbt snapshots implement this pattern automatically.

    Looking up the right surrogate key when loading facts (the version current at the time of the event):

    SELECT f.*, COALESCE(d.customer_sk, -1) AS customer_sk
FROM   stg_sales f
LEFT JOIN dim_customer d
       ON  d.customer_id = f.customer_id
       AND f.order_date >= d.effective_from
       AND f.order_date <= d.effective_to;

    Classic SCD2 bugs to avoid: overlapping date ranges for one customer (fact rows join twice → fan-out); gaps between ranges (facts fall into no version → unknown); more than one is_current = TRUE row per customer. Add data tests for all three (Part 11).

    8.7 Star vs Snowflake vs One Big Table

    Analogy. - Star schema: a star, with the fact table in the centre and each dimension one hop away. Like a cafeteria where every food station is directly reachable from the central seating area. - Snowflake schema: dimensions branch into sub-dimensions (product → subcategory → category → department), like a snowflake's crystal arms. To get to dessert you walk through three connecting rooms. - One Big Table (OBT): a thali — everything already on one plate.

    Aspect Star Snowflake One Big Table
    Joins per query Few More None
    Redundancy Some (in dimensions) Least Most
    Ease for BI users High Lower Highest
    Handling SCD/history Good Good Hard (history must be baked in)
    Maintenance Moderate Higher Simple to query, heavy to rebuild

    Default to a star schema. Columnar compression makes the storage savings of snowflaking negligible, while extra joins cost performance and usability. Use OBTs as derived consumption tables built from the star schema for specific dashboards or ML features, not as your system of record.

    Part 9: Loading data: ETL and ELT patterns

    9.1 ETL vs ELT: Cooking at Home vs in the Restaurant Kitchen

    Analogy. - ETL (Extract → Transform → Load): you cook the meal at home (on a separate transformation server) and deliver the finished dish to the restaurant. The restaurant only ever sees the final dish. If the customer wants it spicier, you go home and cook again. - ELT (Extract → Load → Transform): you deliver raw groceries straight into the restaurant's large professional kitchen (the warehouse), and cook there using its powerful equipment. The raw groceries stay in the pantry, so you can cook a different dish later without going shopping again.

    ETL ELT
    Where transformation runs External engine (SSIS, Informatica, Talend, Spark cluster) Inside the warehouse (SQL, dbt, stored procedures, Spark SQL)
    Raw data kept? Often not Yes (bronze/raw layer)
    Reprocessing Re-extract from source Re-run transforms on stored raw data
    Fits On-prem warehouses with limited compute; heavy pre-load cleansing/PII removal Cloud warehouses with elastic compute

    Modern stacks are mostly ELT, with some ETL-style steps where data must be filtered or masked before landing (e.g., removing PII that must never be stored).

    9.2 Extraction Strategies

    Full load — recounting the entire stock every morning. Extract everything every run. Simple and self-correcting (also captures deletes), but expensive for large tables and heavy on the source. Fine for small reference tables (countries, product categories).

    Incremental by watermark — the bookmark.

    Analogy: you read a book a little each night and use a bookmark. Next night you start from the bookmark, not page one.

    Store the highest updated_at (or an increasing ID) successfully loaded; next run extracts rows WHERE updated_at > :last_watermark.

    -- 1. Read watermark
SELECT last_value FROM etl_watermark WHERE table_name = 'orders';   -- e.g. 2024-10-13 23:00:00

-- 2. Extract with an overlap window for safety
SELECT * FROM src.orders
WHERE updated_at > TIMESTAMP '2024-10-13 23:00:00' - INTERVAL '2 hours'
  AND updated_at <= :run_upper_bound;

-- 3. After a successful load, advance the watermark to :run_upper_bound

    Watermark pitfalls and fixes: - Hard deletes are invisible (a deleted row has no updated_at to see). Fixes: soft deletes in source, periodic full key comparison, or CDC. - Late commits: a transaction that started at 22:59 but committed at 23:05 has updated_at = 22:59, below a watermark you may already have passed. Fix: an overlap window (re-read the last N minutes/hours) plus deduplication downstream. - Unreliable updated_at: some applications forget to update it. Verify with the source team, or use database-maintained columns/triggers/rowversion (ROWVERSION in SQL Server is ideal: an automatically increasing value on every change). - Fixed upper bound: capture :run_upper_bound at the start of the run, so rows changing during the extract are picked up next time consistently. - Index the watermark column in the source, otherwise every incremental query is a full scan.

    CDC — the CCTV footage (Section 6.4). Best completeness and lowest source impact.

    Snapshot comparison — "spot the difference". Compare today's full extract to yesterday's (via EXCEPT or hash comparison) to derive inserts, updates and deletes. A fallback when the source offers no timestamps or CDC.

    9.3 Idempotency: The Light Switch, Not the Toggle Button

    Analogy. A light switch with a clear ON position is idempotent: pressing ON five times leaves the light on. A toggle button is not: pressing it five times leaves the light on or off depending on how many times you pressed. Lift buttons are idempotent too: pressing "5" ten times still takes you to floor 5 once.

    An idempotent pipeline produces the same final result whether it runs once or many times for the same input period. This is the single most important property for reliable pipelines, because in real life jobs fail and get retried, schedulers double-trigger, and you'll need backfills.

    Non-idempotent (dangerous):

    INSERT INTO fact_sales SELECT ... FROM stg_sales WHERE order_date = '2024-10-13';
-- run twice = double sales

    Idempotent patterns:

    -- 1. Delete-insert by period, in one transaction
BEGIN;
DELETE FROM fact_sales WHERE date_key = 20241013;
INSERT INTO fact_sales (...) SELECT ... FROM stg_sales WHERE order_date = '2024-10-13';
COMMIT;

-- 2. Partition overwrite (Databricks / Spark)
INSERT OVERWRITE fact_sales PARTITION (order_date = '2024-10-13')
SELECT ... FROM stg_sales WHERE order_date = '2024-10-13';

-- 3. MERGE on the grain's business key (order_number, order_line)
MERGE INTO fact_sales t USING stg_sales s
  ON t.order_number = s.order_number AND t.order_line = s.order_line
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

    Also: parameterise every job by its logical date (the business period it processes), not "now()". Then "re-run 13 October" means exactly the same thing next week as it did yesterday.

    9.4 Late-Arriving Data

    Late-arriving facts — homework handed in late.

    Analogy: a student submits homework three days late. The teacher still records it against the original due date, not today.

    A sale from 10 October arrives on 14 October (a store's till was offline). Approaches: process a rolling reprocessing window (e.g., each day reload the last 7 days idempotently); or partition by event date and MERGE late rows into the correct partition. Always look up the dimension version effective on the event date, not the load date (Section 8.6).

    Late-arriving (early-arriving fact) dimensions — the "guest pending" name tag.

    Analogy: a conference attendee arrives before their registration has been processed. Instead of turning them away, you hand them a badge saying "Guest — name pending" with their booking number. When the registration comes through, you update the badge.

    A fact references customer C999 but C999 isn't in dim_customer yet. Options: 1. Inferred member (preferred): insert a placeholder dimension row with the business key and 'Unknown' attributes, flagged is_inferred = TRUE; the fact uses its real surrogate key. When the real customer record arrives, update the inferred row in place (Type 1 style, even for SCD2 attributes), then apply normal SCD2 from then on. 2. Point the fact to the -1 Unknown member and re-key later (more work). 3. Hold the fact in a suspense table until the dimension arrives (delays reporting).

    9.5 Bulk Loading: Use the Trolley

    Row-by-row inserts are the slowest possible way to load data. Use the platform's bulk path:

    • PostgreSQL COPY; SQL Server BULK INSERT, bcp, or bulk APIs with batch sizes; Synapse COPY INTO / PolyBase; Snowflake COPY INTO from stages (and Snowpipe for continuous); Redshift COPY from S3; BigQuery load jobs; Databricks COPY INTO / Auto Loader.
    • Load files of sensible size (often 100–250 MB compressed for warehouse loaders) in parallel, rather than one giant file or millions of tiny ones.
    • Prefer columnar, typed, compressed formats (Parquet) over CSV; CSV has no types, ambiguous quoting/escaping, and encoding issues.

    Staging pattern — the loading dock.

    Analogy: deliveries arrive at the loading dock, are inspected and counted, and only then moved onto the shop floor.

    1. Load raw files into a staging table (truncated each run).
    2. Validate: row counts, schema, nulls in keys, duplicates, reference checks.
    3. Transform and publish to the target in one transaction (or partition swap).
    4. Record batch metadata (batch ID, file names, row counts, start/end times, status).

    9.6 Audit Columns and Batch Metadata: Labels on Every Box

    Add to every warehouse table: load_batch_id, loaded_at, source_system, optionally source_file and record_hash. Maintain an ETL control/log table with each run's status and counts. When an analyst asks "why did yesterday's number change?", these let you answer in minutes instead of days.

    9.7 Schema Drift: The Supplier Changed the Box Size

    Analogy: a supplier suddenly sends goods in a different box size without telling you. Your shelves don't fit, or worse, items get placed on the wrong shelf.

    Sources add, rename, reorder, or retype columns. Detect it automatically by comparing incoming schemas to expected ones. Choose a policy per layer: in bronze, accept new columns (schema evolution); in silver/gold, fail loudly on breaking changes (renamed/removed/retyped columns) rather than silently loading NULLs or misaligned data. Data contracts with source teams (Section 11.4) reduce surprises.

    Part 10: Warehouse engines and physical design

    10.1 Columnar Storage: Filing Survey Forms by Question

    Analogy. A company collects 1 million survey forms, each with 100 questions. - Row storage: keep each person's whole form together. Perfect for "show me everything Priya answered" (an OLTP-style lookup). - Column storage: cut the forms apart and keep all answers to Question 7 in one folder, all answers to Question 8 in another. To answer "what's the average rating for Question 7?", you open just one folder instead of reading a million full forms.

    And because the Question 7 folder contains only ratings 1–5, repeated over and over, it compresses beautifully ("1 million entries: mostly 4s and 5s").

    Warehouses store data column by column, so analytical queries read only the columns referenced and benefit from heavy compression (run-length, dictionary, delta encoding), often 5–10x. Each storage block also carries metadata (min/max values per column — zone maps), so the engine can skip blocks that can't contain matching rows.

    Consequences for you: - SELECT * is far more expensive than in OLTP: every extra column is extra I/O and, in BigQuery's on-demand pricing, extra cost. - Single-row updates and deletes are expensive (columns must be rewritten in blocks); warehouses prefer batch inserts and set-based MERGE. - Sorting/clustering data on commonly filtered columns makes zone maps more effective.

    10.2 MPP: Many Checkout Lanes

    Analogy. One cashier serving 1,000 customers takes all day. Twenty cashiers take a fraction of the time — if customers are spread evenly across the lanes. If 900 customers queue at lane 3 because it's nearest the door, the other 19 cashiers sit idle and you've gained almost nothing. That's skew.

    Massively Parallel Processing (MPP) splits data across many compute nodes/slices; each processes its portion in parallel, then results are combined. Redshift, Synapse dedicated pools, Teradata, Greenplum, and (internally) Snowflake, BigQuery and Databricks/Spark all work this way.

    Distribution: Seating Group-Project Teams in the Same Room

    Analogy. Students are assigned to classrooms. If every group project team is placed in the same classroom, teams can work immediately. If team members are scattered across rooms, they waste time running between rooms to talk (data shuffling / redistribution over the network).

    In MPP systems where you choose distribution (Redshift, Synapse dedicated pools):

    • Hash distribution on a join key (e.g., customer_sk) places matching rows from two large tables on the same node, so joins happen locally with no data movement. Choose a high-cardinality, evenly distributed column that's frequently used in joins/aggregations, and that isn't frequently filtered to a single value.
    • Replicate (ALL) small dimensions to every node, so every node can join locally.
    • Round-robin (EVEN) spreads rows evenly with no key; good for staging tables, but joins will need data movement.
    • Avoid skewed keys: a column where one value has most rows (e.g., country when 80% of customers are in one country, or a key with many -1 Unknown values) concentrates work on one node.

    Sorting and Clustering: Labelled Boxes in a Storage Unit

    Analogy. If receipts in a storage unit are boxed by month with the month written on each box, finding March receipts means opening only the March box. If receipts were thrown into boxes randomly, every box would have some March receipts.

    Physically ordering data by a commonly filtered column (usually date) makes block skipping (zone maps) highly effective.

    10.4 The Small-Files Problem: Thousands of Sticky Notes

    Analogy. Reading one 300-page book is fast. Reading the same content written on 300,000 sticky notes — finding, opening, and reading each one — takes forever, even though it's the same amount of text.

    In lakehouses (and loaders like Snowpipe, streaming ingestion), frequent small writes produce huge numbers of tiny files. Each file has open/metadata overhead, so queries slow down dramatically. Fixes: compaction (OPTIMIZE in Delta, rewrite/compaction procedures in Iceberg), larger write batches, auto-optimise features, and avoiding over-partitioning (partitioning on a high-cardinality column like customer_id creates millions of tiny files).

    10.5 Materialised Views, Aggregate Tables and Caching

    Analogy: a restaurant pre-makes its most popular sauce in the morning rather than starting from scratch for every order.

    For expensive, frequently repeated queries (daily sales by store and category), pre-compute aggregate tables or materialised views. Many BI tools also support aggregation awareness. Snowflake and BigQuery cache query results for identical queries on unchanged data; Power BI import models and semantic-layer caches also help. Trade-off: freshness and storage vs speed.

    10.6 Cost Management: The Taxi Meter Is Always Running

    Analogy. In an on-prem data centre you bought the car; driving more costs little extra. In the cloud you're in a taxi: the meter runs while compute is on, and every kilometre (byte scanned, second of compute) is billed.

    In the cloud, performance tuning and cost control are the same job: - Scan less: partition and cluster on filter columns; select only needed columns; avoid repeatedly scanning raw tables. - Run less: incremental models instead of full rebuilds; schedule only what's needed (does that dashboard really need refreshing every 5 minutes?). - Size right: match warehouse/cluster size to the workload; bigger isn't always faster for small queries; set auto-suspend (e.g., 60 seconds) and auto-terminate. - Guardrails: resource monitors, budgets and alerts, query timeouts, maximum bytes billed (BigQuery). - Attribute costs: separate warehouses/projects/tags by team or workload, so every team sees its own bill. - Storage hygiene: expire old snapshots, tune Time Travel retention, drop unused tables and clones.

    Part 11: Data quality, governance and trust

    11.1 Data Quality: Quality Control on the Factory Line

    Analogy. A biscuit factory checks biscuits at several stations — weight, shape, colour, packaging seal. A defective biscuit caught at the first station costs a fraction of one that reaches a customer and causes a recall.

    A wrong number on an executive dashboard destroys trust that takes months to rebuild. Test data at every layer, as close to ingestion as possible.

Tools: dbt tests (and packages like dbt-expectations), Great Expectations, Soda, Monte Carlo / data observability platforms, or plain SQL checks orchestrated after each load.

    11.2 Reconciliation: Counting the Cash Drawer at Closing

    Analogy. At closing time, the cashier counts the cash drawer and compares it to the till's total. If they don't match, nobody goes home until the difference is explained.

    SELECT 'source' AS side, COUNT(*) AS row_count, SUM(amount) AS total
FROM   src_sales WHERE sale_date = '2024-10-13'
UNION ALL
SELECT 'warehouse', COUNT(*), SUM(net_amount)
FROM   fact_sales WHERE date_key = 20241013;

    Reconcile counts and key sums at each hop (source → bronze → silver → gold). Store the results in a reconciliation table so you have an audit trail, and alert on differences beyond an agreed tolerance (which should usually be zero for financial data).

    11.3 Governance: Library Catalogue, Family Tree and Ingredient Labels

    Data catalogue — the library catalogue.

    Without a catalogue, a library with a million books is useless: you can't find anything, and you don't know which edition is authoritative.

    Document every important table and column: description, owner, grain, refresh schedule, sensitivity classification, and certified/"golden" status. Tools: Microsoft Purview, Unity Catalog, Collibra, Alation, DataHub, Atlan, dbt docs.

    Lineage — the family tree / food supply chain.

    When there's a food contamination scare, a good supply chain can trace exactly which farm, truck and warehouse every packet came through, and which shops received packets from the bad batch.

    Lineage shows which sources feed which tables, and which tables feed which reports. Use it for impact analysis ("if I change this column, which dashboards break?") and root-cause analysis ("this KPI is wrong — which upstream table caused it?").

    Classification and privacy — ingredient and allergen labels. Tag PII and sensitive data (names, emails, phone numbers, national IDs, health, financial data) and apply controls automatically by tag (masking, restricted roles). Respect applicable laws — e.g., India's DPDP Act 2023, the EU GDPR, Australia's Privacy Act — including purpose limitation, retention limits, and rights such as erasure. Design for erasure early: deleting one person from SCD2 history, backups, and immutable raw layers is hard if not planned (techniques: keep PII in a separate, deletable table keyed by surrogate; crypto-shredding by deleting per-person encryption keys).

    11.4 Data Contracts: The Rental Agreement

    Analogy. A rental agreement spells out what the landlord provides, what the tenant may do, notice periods for changes, and what happens if either side breaks the terms. It prevents surprise evictions.

    A data contract between a producing team and the data platform defines schema, meaning of fields, data types, allowed values, freshness and volume expectations, and the change process (e.g., "breaking changes need 30 days' notice and a versioned schema"). Contracts can be enforced in CI (schema checks on the producer's side) so breaking changes fail before they reach your pipeline.

    Part 12: Orchestration, DevOps and operations

    12.1 Orchestration: The Air Traffic Controller

    Analogy. An air traffic controller doesn't fly planes. She decides which plane takes off when, in what order, keeps them apart, reroutes them when a runway closes, and raises the alarm if one goes missing.

    An orchestrator (Apache Airflow, Azure Data Factory, Dagster, Prefect, dbt Cloud, Databricks Workflows, Fabric pipelines) schedules jobs, manages dependencies (load dimensions before facts), handles retries, tracks state, and alerts on failures and missed SLAs.

    Good orchestration practices: - Tasks are idempotent and parameterised by logical date (Section 9.3). - Dependencies are explicit (task graph / DAG), not "job B is scheduled 30 minutes after job A and we hope A finishes in time". - Retries with backoff for transient errors (network blips, deadlock victims, throttling); no retries for logic errors (bad data won't fix itself). - Backfills are a first-class operation: "re-run 1–15 October" is one command. - Sensors / event triggers wait for upstream data to actually arrive. - SLAs and freshness alerts fire when data is late, not just when a job errors. - Keep orchestration code thin: the orchestrator calls SQL/dbt/Spark; business logic doesn't live inside the scheduler config.

    12.2 Engineering Practices for SQL Code

    Analogy: a professional kitchen has standard recipes, labelled containers, a head chef who tastes before dishes go out, and a strict separation between the prep area and the serving counter.

    • Version control: every SQL file, DDL migration, dbt model and pipeline definition is in Git.
    • Code review: every change goes through a pull request; reviewers check logic, grain, joins, performance and tests.
    • Environments: separate dev, test/UAT, prod with separate credentials and data. Developers don't work directly in prod.
    • CI/CD: on each pull request, automatically compile/lint (e.g., sqlfluff), run unit tests and data tests on sample or slim CI data; on merge, deploy to test and then prod.
    • Modularity: small, layered models (stg_ → int_ → dim_/fact_ → mart_) rather than 3,000-line stored procedures. dbt has made this the industry norm.
    • Naming conventions: consistent snake_case; prefixes per layer; plural vs singular chosen once; date columns ending in _date, timestamps in _ts or _at, booleans starting with is_/has_, surrogate keys ending in _sk.
    • Documentation next to code: model descriptions, column descriptions and the declared grain in YAML/docs.

    12.3 Incident Management: Hospital Triage

    Analogy. An emergency department doesn't treat patients in arrival order; it triages — the most critical first — stabilises them, treats the cause, and later reviews what could be done better.

    When a pipeline fails or data is wrong:

    1. Detect — ideally through your own alerts, before users notice.
    2. Assess impact — which tables, dashboards, users, and decisions are affected? Use lineage.
    3. Communicate early — a short message to stakeholders ("Sales dashboard delayed; data for 13 Oct not yet loaded; next update 10:00") prevents people acting on bad numbers.
    4. Contain — stop bad data spreading (pause downstream jobs, keep the last good version published).
    5. Fix — fix forward or roll back; re-run idempotent jobs; backfill affected periods.
    6. Verify — data tests and reconciliation pass.
    7. Post-mortem (blameless) — timeline, root cause, why detection took as long as it did, and concrete prevention actions (a new test, an alert, a contract with the source team).

    Maintain runbooks for known failure types (source unavailable, schema drift, duplicate files, warehouse out of credits) so on-call engineers aren't relying on one person's memory.

    Scenario: A retailer with 300 stores and an e-commerce site wants daily sales reporting by product, store, customer segment and promotion, with historically accurate customer regions, available by 07:00 every day.

    Step 1 — Requirements (ask before you build). Which questions must be answered? Who uses it (BI tool, analysts, finance)? Freshness (daily by 07:00)? History depth (3 years plus ongoing)? Volume (~2 million order lines/day)? Sensitive data (customer PII)? Which numbers must reconcile with finance?

    Step 2 — Source analysis. POS database (SQL Server, one per region), e-commerce database (PostgreSQL), CRM (REST API), promotions (spreadsheet maintained by marketing).     Step 3 — Ingestion (bronze).     Step 4 — Cleansing and conforming (silver).     Step 5 — Dimensional model (gold). - fact_sales — grain: one row per order line. - fact_inventory_daily — periodic snapshot: one row per product per store per day. - dim_date, dim_product (Type 1 for name corrections, Type 2 for category changes), dim_customer (Type 2 on region and segment; PII columns masked), dim_store, dim_promotion, dim_order_flags (junk dimension: channel, payment type, gift flag). - Unknown members (-1) in every dimension; inferred members for late-arriving customers.

    Step 6 — Physical design. Fact partitioned by date_key (or clustered by date in Snowflake/BigQuery) and clustered by store_sk, product_sk. In an MPP engine with explicit distribution: hash-distribute fact_sales on customer_sk or product_sk (check for skew), replicate small dimensions.

    Step 7 — Loading logic. Order: dimensions (SCD2 merge) → facts. Facts loaded with delete-insert for a rolling 7-day window to absorb late transactions. Surrogate key lookup by event date. Whole publish step in a transaction or partition swap.

    Step 8 — Quality gates. Grain uniqueness, orphan keys, SCD2 integrity, volume anomaly checks per store, source-to-gold reconciliation of counts and amounts per day per store, freshness check at 06:30. Hard-fail rules keep yesterday's published data visible rather than publishing wrong numbers.

    Step 9 — Security. Analysts: read on gold marts only. PII masked for everyone except a small pii_reader role. Row-level security by region for regional managers. Pipelines run under a managed identity; secrets in Key Vault.

    Step 10 — Operations. Orchestrated DAG with retries and SLA alert at 06:45; dashboards for runtime trend, cost per run and row counts; runbook for common failures; quarterly restore test; monthly access review; documentation in the catalogue with owners and grain statements.

    15.2 Interview Questions with Model Answers (Short Form)

    1. ROW_NUMBER vs RANK vs DENSE_RANK? For ties: ROW_NUMBER gives unique sequential numbers (arbitrary order for ties unless a tie-breaker is added); RANK gives ties the same rank and leaves gaps (1,2,2,4); DENSE_RANK gives ties the same rank without gaps (1,2,2,3).

    2. Why does NOT IN return no rows when the subquery has a NULL? x NOT IN (a, b, NULL) expands to x<>a AND x<>b AND x<>NULL; the last term is UNKNOWN, so the whole expression is never TRUE. Use NOT EXISTS.

    3. Clustered vs non-clustered index; what's a covering index? Clustered defines the physical order of the table (one per table, like a dictionary). Non-clustered is a separate sorted structure pointing to rows (like a textbook index). A covering index contains all columns a query needs (via key or INCLUDE columns), avoiding lookups.

    4. Why might the optimiser ignore an index? Non-sargable predicate (function on column, implicit conversion, leading wildcard); the query returns a large fraction of the table so a scan is cheaper than many lookups; leading column of a composite index not used; stale statistics; parameter sniffing.

    5. Isolation levels and anomalies? Read Uncommitted allows dirty reads; Read Committed prevents dirty reads but allows non-repeatable reads and phantoms; Repeatable Read prevents non-repeatable reads (phantoms possible by the standard); Serializable prevents all including write skew. MVCC engines implement these with snapshots instead of read locks.

    6. What causes deadlocks and how do you prevent them? Two transactions each holding a lock the other needs. Prevent with consistent access order, short transactions, proper indexing, snapshot-based isolation for readers, and retry logic for victims.

    7. Star vs snowflake? Star: denormalised dimensions one join from the fact — simpler and usually faster. Snowflake: normalised dimension hierarchies — less redundancy, more joins. Default to star in modern columnar warehouses.

    8. Explain and implement SCD Type 2. Preserve history by expiring the current row and inserting a new row with a new surrogate key and validity dates when tracked attributes change. Facts link to the version valid at event time. (See Section 8.6 for the two-step SQL.)

    9. What is grain and why is it so important? What one fact row represents. It determines which dimensions and facts are valid; mixing grains causes double counting. Choose the lowest atomic grain available.

    10. Additive vs semi-additive vs non-additive facts? Additive sum across all dimensions (sales); semi-additive not across time (balances); non-additive never summed (ratios) — store components and compute at query time.

    11. Handling late-arriving facts and dimensions? Facts: rolling reprocessing windows, partitioned by event date, SCD lookup by event date. Dimensions: inferred members updated when real data arrives, or unknown member with later re-keying.

    12. How do you make a pipeline idempotent? Process by logical date; publish with delete-insert in a transaction, partition overwrite/swap, or MERGE on the grain key; never blind appends; deduplicate staging deterministically.

    13. Watermark incremental vs CDC? Watermark is simple but misses hard deletes and late commits, and needs a reliable indexed timestamp. CDC reads the transaction log, captures all changes including deletes with low source impact, but needs more setup and careful application of change streams.

    14. Choosing a distribution key; what is skew? Pick a high-cardinality, evenly distributed, frequently joined column so large-table joins are co-located; replicate small dimensions. Skew is uneven distribution that overloads some nodes and makes queries as slow as the busiest node.

    15. A query went from 2 to 40 minutes. How do you investigate? Check what changed (data volume, code, statistics, plan, concurrency/blocking, warehouse size). Compare actual plans old vs new (Query Store / query history), look for estimate/actual mismatches, spills, scans; check stats freshness and blocking; fix and re-measure.

    16. RPO and RTO; design a backup strategy for a 15-minute RPO. RPO = acceptable data loss, RTO = acceptable downtime. For 15-minute RPO: full weekly, differential daily, log backups every 5–15 minutes, stored off-site/immutable, with regular test restores timed against the RTO.

    17. How do you reconcile source and warehouse? Compare counts and key sums per period (and per partition such as store) at each layer; use EXCEPT or hash comparisons for row-level differences; store results and alert on variances.

    18. DELETE vs TRUNCATE vs DROP? DELETE removes chosen rows, fully logged, fires triggers, can be rolled back; TRUNCATE removes all rows quickly with minimal logging, resets identity (in SQL Server) and needs higher privilege; DROP removes the table definition and data entirely.

    19. UNION vs UNION ALL; WHERE vs HAVING? UNION de-duplicates (extra sort/hash); UNION ALL keeps all rows and is faster. WHERE filters rows before grouping; HAVING filters groups after aggregation.

    20. How do you implement row-level security and PII masking? RLS with policies that filter rows by the user's attributes (PostgreSQL policies, SQL Server security policies, Snowflake row access policies). Masking with dynamic masking/masking policies by role, plus column grants, tokenisation in lower environments, and classification tags driving controls.
